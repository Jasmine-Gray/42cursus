### ステップ1：プログラムの入り口（`main`関数）

一番最初に実行されるのは `main.cpp` の `main` 関数です。ここでは、ユーザーが入力した引数（ポート番号とパスワード）をチェックし、`Server` クラスの実体（インスタンス）を作成して起動をかけます。

**該当コード (`main.cpp`)**

```cpp
// 引数のチェック後...
Server server(port, argv[2]); // 1. サーバーオブジェクトの作成
return server.run();          // 2. サーバーのメイン処理を開始

```

### ステップ2：サーバーの起動準備（`Server::run`メソッド）

`server.run()` が呼ばれると、`Server.cpp` の `Server::run` メソッドに処理が移ります。ここでシグナル（`Ctrl+C` などによる終了要求）の設定を行い、**実際のネットワーク通信のセットアップ関数**を呼び出します。

**該当コード (`Server.cpp` の `run` 内)**

```cpp
int Server::run()
{
    g_stopRequested = 0;
    signal(SIGPIPE, SIG_IGN);
    signal(SIGINT, handleStopSignal);
    signal(SIGTERM, handleStopSignal);
    
    // ↓ ★ここがネットワーク立ち上げの核心部分！
    if (!setupListenSocket()) 
        return 1;
        
    std::cout << "Server is listening on port " << port_ << std::endl;
    // ...この後、poll() の無限ループ（通信待ち状態）に突入します

```

### ステップ3：通信回線の開通（`Server::setupListenSocket`メソッド）

この関数が、ネットワークプログラミングにおける「サーバー立ち上げ」の本体です。先ほど解説したシステムコール群が順番に呼ばれています。

**該当コード (`Server.cpp` の `setupListenSocket` 内)**

```cpp
bool Server::setupListenSocket()
{
    sockaddr_in address;
    pollfd      listenPollFd;

    // ① socket: 通信の入り口（電話機）を作成
    serverFd_ = socket(AF_INET, SOCK_STREAM, 0);
    
    // ② fcntl (setNonBlockingの中身): ノンブロッキングモードに設定
    if (!setNonBlocking(serverFd_)) { ... }

    // 設定情報の準備（IPv4、すべてのIPからの接続を許可、指定ポート）
    std::memset(&address, 0, sizeof(address));
    address.sin_family = AF_INET;
    address.sin_addr.s_addr = htonl(INADDR_ANY);
    address.sin_port = htons(static_cast<unsigned short>(port_));

    // ③ bind: ソケットにIPアドレスとポート番号（電話番号）を割り当て
    if (bind(serverFd_, reinterpret_cast<sockaddr *>(&address), sizeof(address)) < 0) { ... }

    // ④ listen: クライアントからの接続待ち（着信待ち）状態にする
    if (listen(serverFd_, SOMAXCONN) < 0) { ... }

    // ⑤ pollへの登録: サーバーの受付用ソケットを監視対象に追加
    listenPollFd.fd = serverFd_;
    listenPollFd.events = POLLIN; // 「データが読み取れるか（新規接続が来たか）」を監視
    listenPollFd.revents = 0;
    pollfds_.push_back(listenPollFd);

    return true;
}

```

### まとめ

1. `main` から `Server::run()` が呼ばれる。
2. `Server::run()` が `Server::setupListenSocket()` を呼び出す。
3. `setupListenSocket()` の中で **`socket` ➔ `bind` ➔ `listen**` の順番でシステムコールが実行され、最後にそのソケットを `poll` の監視リスト（`pollfds_`）に登録して立ち上げ完了！

これ以降、プログラムは `Server::run()` 内の `while` ループに突入し、`poll()` を使ってひたすらクライアントからのアクセスを待ち続ける状態になります。

## signal

---

### 1. `g_stopRequested = 0;`

**【役割】サーバーの停止フラグの初期化（リセット）**

* `g_stopRequested` は、シグナルを受け取ったときに `1` に書き換えられるグローバル変数（`volatile sig_atomic_t`）です。
* `main` 関数から `run()` が呼ばれた際、念のためこのフラグを `0` にリセットしています。これにより、サーバーのメインループ（`while (!g_stopRequested)`）が確実に実行を開始できるようになります。

### 2. `signal(SIGPIPE, SIG_IGN);`

**【役割】クライアント切断時の予期せぬクラッシュ（強制終了）を防ぐ**

* **これがネットワークプログラミングにおいて最も重要な1行です。**
* **SIGPIPEとは：** サーバーが `send()` を使ってクライアントにデータを送ろうとした瞬間に、すでにクライアント側が通信を強制切断（LANケーブルを抜く、アプリを強制キルするなど）していた場合、OSはサーバープログラムに対して「送信先がもう無いよ！」という意味で `SIGPIPE` というシグナルを送ります。
* **なぜ無視するのか：** `SIGPIPE` のデフォルトの挙動は「プロセスの強制終了（クラッシュ）」です。つまり、この1行がないと、誰かが強制切断するだけでサーバー全体が落ちてしまいます。`SIG_IGN` (Signal Ignore) を設定することで、OSによる強制終了を無効化します。
* **無視した後はどうなる？：** 強制終了を免れる代わりに、`send()` 関数が `-1` を返し、`errno` に `EPIPE` がセットされます。あとはコード内のエラーハンドリング（`send() < 0` の処理）で安全にそのクライアントのソケットを閉じる（`closeClient`）だけで済むようになります。

### 3. `signal(SIGINT, handleStopSignal);`

**【役割】Ctrl+C による安全なシャットダウンの準備**

* **SIGINTとは：** ターミナルで `Ctrl+C` が押されたときにOSから送られてくる「割り込み（Interrupt）」シグナルです。
* デフォルトでは `Ctrl+C` を押すとプログラムは即座に強制終了します。しかしそれだと、開いているソケット（ファイルディスクリプタ）が閉じられなかったり、メモリが解放されなかったりする危険があります。
* そこで、即座に終了するのではなく、自作の関数 `handleStopSignal` に処理を横取りさせます。この関数の中で `g_stopRequested = 1` に書き換えることで、`while` ループを抜け出し、デストラクタ等で綺麗にソケットを閉じてからプログラムを終了（Graceful Shutdown）させることができます。

### 4. `signal(SIGTERM, handleStopSignal);`

**【役割】システムからの終了要求に対する安全なシャットダウンの準備**

* **SIGTERMとは：** ターミナルから `kill` コマンドが実行されたり、OS自体がシャットダウンしようとしたときに送られてくる「終了（Terminate）」シグナルです。
* 役割は `SIGINT` と全く同じです。外からの終了要求に対してパニックにならず、フラグを立てて「今やっているループが終わったら、自分で片付けをしてから終わりますね」という安全な挙動を実現するためのものです。

### 1. `socket` の役割

* **一言でいうと：** 通信のエンドポイント（端点）の作成
* **技術的な詳細：** OSに対して「これからネットワーク通信をしたいから、専用のファイル（ファイルディスクリプタ＝FD）を一つ用意して！」と要求するシステムコールです。Unix系OSでは「すべてはファイルである」という思想があるため、ネットワーク通信もこの「ソケット」という特殊なファイルへの読み書きとして扱われます。
* **例え：** 「新しく電話機を買ってきて、電話線を繋ぐこと」です。ただし、この時点ではまだ電話番号はありません。

### 2. `fcntl` (File Control) の役割

* **一言でいうと：** ファイルディスクリプタの性質（フラグ）を変更する
* **技術的な詳細：** `ft_irc`においては、「ソケットをノンブロッキングモード（`O_NONBLOCK`）にする」という超重要ミッションを担います。デフォルトのソケットは、データが来るまでプログラムの動きを止めて（ブロックして）待ち続けます。しかし `fcntl` を使って設定を書き換えることで、「データがないなら、待たずにすぐエラー（`EWOULDBLOCK` など）を返して次の処理へ進む」という止まらない挙動に変更できます。
* **例え：** 「電話機の留守電設定を『相手が喋るまで待ち続けず、無音ならすぐ切る』モードに変更すること」です。

### 3. `bind` の役割

* **一言でいうと：** ソケットに名前（IPアドレスとポート番号）を結びつける
* **技術的な詳細：** 作成されたばかりのソケットは、どこからの通信を受け付けるのか決まっていません。`bind` を使うことで、「このソケットは、IPアドレス『0.0.0.0（すべてのローカルIP）』の、ポート番号『6667』で待機します」とOSに宣言し、特定のポートをサーバー専用として占有（バインド）します。
* **例え：** 「買ってきた電話機に、特定の『電話番号（内線6667番）』を割り当てること」です。これで初めて、外部の人がどこに電話をかければいいかが決まります。

### 4. `listen` の役割

* **一言でいうと：** ソケットを「接続待ち（パッシブ）」状態にする
* **技術的な詳細：** ソケットは通常、自分から誰かに接続しに行く（アクティブ）ことも、誰かからの接続を待つ（パッシブ）こともできます。`listen` を呼び出すことで、OSに対して「このソケットはサーバーの受付用として、外部からのアクセスを待つ専用にします」と宣言します。また、「同時に大量のアクセスが来たとき、何人まで順番待ち（キュー）させるか（`SOMAXCONN` など）」もここで設定します。
* **例え：** 「電話機の電源を入れ、着信音が鳴るようにして『受付窓口をオープン』にすること」です。

### 5. `poll` の役割

* **一言でいうと：** 複数のファイルディスクリプタ（ソケット）の状態を同時に監視する
* **技術的な詳細：** ノンブロッキングサーバーの要（かなめ）です。監視したいソケットのリスト（あなたのコードでの `pollfds_`）を渡すと、OSが「この中から、今データが届いている（`POLLIN`：読み取り可能）ソケットや、データを送信できる（`POLLOUT`：書き込み可能）ソケット」を見つけ出して教えてくれます。これにより、CPUを無駄に回転させることなく、効率よく複数のクライアントを同時にさばくことができます。
* **例え：** 「何十台もの電話機が並ぶコールセンターで、どの電話機が鳴っているか（ランプが点滅しているか）を一目で監視し、『◯番の電話機に応答して！』と指示を出す凄腕のオペレーター」です。

### 6. `accept` の役割

* **一言でいうと：** クライアントからの接続要求を受け入れ、「そのクライアントとの通信専用の新しいソケット」を作成する。
* **技術的な詳細：**
`poll` が「受付用ソケット（`serverFd_`）に読み取り可能なデータがある（`POLLIN`）」と報告してきたとき、それは「新しいクライアントが接続してきた」ことを意味します。
そこで `accept` を呼び出すと、OSは接続要求を取り出し、元の受付用ソケットとは全く別の、新しいファイルディスクリプタ（FD）を生成して返してくれます。以降、そのクライアントとのデータの送受信（`recv` / `send`）は、すべてこの「新しい専用FD」を使って行います。元の受付用ソケットは、そのまま次の新しい着信を待ち続けます。
* **例え：**
「総合受付のオペレーターが電話を取り、『担当者にお繋ぎしますね』と言って、お客様を別の『専用回線（新しいFD）』に転送すること」です。
総合受付の電話（`serverFd_`）でお客様の要件を最後まで聞いてしまうと、その間他の電話に出られなくなってしまいますよね。だから、通話が繋がったらすぐに専用回線に回し、受付はまたすぐ次の着信を待てるようにするわけです。

### あなたのコード（`ft_irc`）での `accept` の動き

あなたの `Server::acceptClients()` メソッドの中で行われていることは、まさにこの「専用回線の手配と登録」です。

1. **`clientFd = accept(...)`**: 新しいクライアント専用の通信回線（FD）を受け取ります。
2. **`setNonBlocking(clientFd)`**: この専用回線も「ノンブロッキングモード（相手が喋るまで待ち続けない設定）」にします（ここも `fcntl` の出番です！）。
3. **`pollfds_.push_back(...)`**: 凄腕の監視役である `poll` に、「この新しい専用回線も監視リストに加えて！お客さんが喋ったら教えて！」と依頼します。
4. **`clients_.insert(...)`**: サーバー内部の名簿（`std::map`）に、この専用回線の番号（FD）と紐づけて、新しいお客様のカルテ（`ClientSession`）を作成します。


ここまでの `socket` ➔ `bind` ➔ `listen` ➔ `poll` ➔ `accept` の流れが、ノンブロッキングサーバーの骨格です。

`recv`（レシーブ）は、C言語やC++のネットワークプログラミングにおいて、「接続されたソケット（通信の窓口）からデータを受け取る（読み込む）」ためのシステムコール（OSの機能への命令）です。

あなたの作成している `ft_irc` サーバーにおいて、クライアント（IrssiやWeeChatなど）から送られてきたチャットメッセージやコマンド（`JOIN` や `PRIVMSG` など）をプログラム内に取り込むための非常に重要な役割を担っています。

分かりやすくイメージするために、基本的な仕組みと使い方を詳しく解説します。

---

### 1. `recv` の仕組み（郵便受けのイメージ）

ネットワーク越しにクライアントからデータが送られてくると、そのデータはいきなりあなたのプログラム（C++のコード）に届くわけではありません。まずは、OS（MacやLinuxなど）が用意している「受信バッファ（郵便受け）」に一時的に貯められます。

`recv` 関数の役割は、「OSの郵便受けに貯まっているデータを取り出して、プログラム内で使える変数（配列）にコピーすること」です。

### 2. `recv` の基本的な書き方と引数

C言語の標準的な定義は以下のようになっています。

```c
ssize_t recv(int sockfd, void *buf, size_t len, int flags);

```

あなたのコード（`recv(fd, buffer, sizeof(buffer), 0)`）に当てはめると、それぞれの意味はこうなります。

* **第1引数 `sockfd` (`fd`)**: どのクライアントからデータを読み込むか（ファイルディスクリプタ）。
* **第2引数 `buf` (`buffer`)**: 読み込んだデータを保存する場所（自分で用意した `char` 型の配列など）。
* **第3引数 `len` (`sizeof(buffer)`)**: 一度に読み込む最大サイズ（用意した配列の大きさを超えないようにするため）。
* **第4引数 `flags` (`0`)**: 特殊な読み込み方を指定するフラグ（通常は `0` でOKです）。

### 3. 最も重要な「戻り値」の理解

`recv` を実行した結果（戻り値）は `ssize_t` 型（符号付き整数）で返ってきます。この数値によって、**次にプログラムが何をすべきか**を絶対に分岐させなければなりません。

* **戻り値が `1` 以上（成功）**
* 意味：無事にデータを受信できた。数値は「実際に読み込んだバイト数」です。
* 注意：クライアントが「100バイト」のメッセージを送ってきても、1回の `recv` で「30バイト」しか受け取れないこともあります（残りは次の `recv` で受け取る）。


* **戻り値が `0`（切断）**
* 意味：クライアントが通信を「正常に切断（終了）」したサイン（EOF：End Of File）です。
* 対応：サーバー側でも、このクライアントのソケットを `close(fd)` して、ユーザーリストから削除する処理を行う必要があります。


* **戻り値が `-1`（エラーまたは待機）**
* 意味：何らかのエラーが発生した。このとき、詳細なエラーの原因が `errno` というグローバル変数にセットされます。
* **【超重要】ノンブロッキング通信の場合**：あなたのサーバーのように `fcntl(fd, F_SETFL, O_NONBLOCK)` でノンブロッキング設定をしていると、「今はまだ郵便受けにデータが届いていないよ」という場合でもプログラムを止めずに `-1` を返します。この時の `errno` が、先ほど登場した **`EAGAIN`** や **`EWOULDBLOCK`** です。



### 4. `ft_irc` における `recv` と `poll` の関係

前回のReview項目の話に繋がりますが、ノンブロッキング通信において `recv` をやみくもに呼び出すのは非効率です。データがないのに `recv` を呼んで `-1 (EAGAIN)` を受け取る作業を繰り返すと、CPUを無駄に消費してしまいます。

そこで **`poll`** の出番です。

1. **`poll`**: 「◯番のソケット（郵便受け）にデータが届くまで待機して、届いたら教えて！」とOSにお願いする。
2. データが届くと `poll` が反応し、`POLLIN` というフラグを立てる。
3. **`recv`**: `POLLIN` が立っているソケットに対してだけ、確実に1回 `recv` を実行してデータを回収する。

このように役割分担をすることで、エラー（`EAGAIN`）をチェックすることなく、データがある時だけ無駄なく処理を行う「イベント駆動」の美しいサーバーを作ることができます。

## address


前のステップで `socket()` を使って「空の電話機」を用意しましたよね。この4行は、その電話機に割り当てるための「IPv4・すべてのIPアドレス・指定ポート」という設定データ（`sockaddr_in` 構造体）を準備する作業になります。


---

### 1. `std::memset(&address, 0, sizeof(address));`

**【やっていること】設定用紙を「真っ白（ゼロ）」にリセットする**

* `address`（`sockaddr_in`構造体）のメモリ領域をすべて `0` で埋めています。
* **なぜ必要？：** C++の構造体は、作成された直後はメモリ上に昔の「ゴミデータ」が残っていることがあります。また、この構造体にはOSの都合で「使わない余白（パディング）」が含まれています。ここを綺麗に `0` で初期化しておかないと、後で `bind` を実行したときにOSが混乱してエラーを起こす原因になります。

### 2. `address.sin_family = AF_INET;`

**【やっていること】「IPv4」のルールで通信することを宣言する**

* `sin_family` は「通信プロトコルの種類」を指定する項目です。
* `AF_INET` を指定することで、「192.168.1.1 のような、ごく一般的なIPv4形式のIPアドレスを使いますよ」とOSに伝えます。

### 3. `address.sin_addr.s_addr = htonl(INADDR_ANY);`

**【やっていること】「どのIPアドレスからの着信も受け付ける」と設定する**

* `INADDR_ANY` は「0.0.0.0」を意味し、「このPCが持っているすべてのネットワーク（ローカルループバックや、Wi-FiのIPなど）のどこにアクセスしてきても応答します」という設定です。
* 💡 **超重要 `htonl()` の役割：**
* これは **H**ost **TO** **N**etwork **L**ong の略です。
* 実は、私たちが普段使っているパソコンのCPU（IntelやApple Siliconなど）と、インターネットの世界（ネットワーク）とでは、**数字の読み書きの方向（エンディアン）が逆**なんです（パソコンは右から左へ、ネットワークは左から右へ数字を読みます）。
* この `htonl()` は、IPアドレスの数字を「パソコン語（リトルエンディアン）」から「インターネット語（ビッグエンディアン）」へと翻訳する役割を持っています。これがないと、ネットワーク側が数値を正しく読めません。



### 4. `address.sin_port = htons(static_cast<unsigned short>(port_));`

**【やっていること】待機する「ポート番号（例：6667）」を設定する**

* コマンドライン引数で受け取った `port_` の数値をセットしています。
* 💡 **超重要 `htons()` の役割：**
* こちらは **H**ost **TO** **N**etwork **S**hort の略です。（`Long` は32ビットのIP用、`Short` は16ビットのポート番号用です）。
* 先ほどの `htonl()` と全く同じ理由で、ポート番号を「インターネット語」に翻訳しています。

### まとめ

この4行が終わった時点で、**「IPv4プロトコルで、すべてのIPアドレスを受け付け、翻訳済みの6667番ポートを使用する」という完璧な設定データ（`address`）が完成**します。

そして、この直後に呼ばれる `bind(serverFd_, ...)` によって、ようやく「空の電話機（`serverFd_`）」に「この設定データ（`address`）」がガチャンと紐付けられる（バインドされる）わけです。

## listen

この4行は、「凄腕の監視役である `poll` に提出するための『監視依頼書（`pollfd` 構造体）』を作成し、リストに登録する」という重要な作業をしています。

この依頼書（構造体）には「どの電話機で」「どんな変化があったら教えてほしいか」を書き込む必要があります。1行ずつ裏側で起きていることを解説しますね！

### 1. `listenPollFd.fd = serverFd_;`

**【やっていること】「どのソケット（電話機）」を監視するかを指定する**

* `pollfd` 構造体の `fd` (File Descriptor) という項目に、先ほど設定を終えたサーバーの受付用ソケット（`serverFd_`）の番号をセットしています。
* これにより、OSに対して「この依頼書は、受付用の電話機についてのものです」とターゲットを明確に指定しています。

### 2. `listenPollFd.events = POLLIN;`

**【やっていること】「どんな変化（イベント）」を監視するかを指定する**

* `events` は、OSに対して「このソケットに何が起きたら教えてほしいか（監視の目的）」を伝えるフラグです。
* `POLLIN` (Poll In) は「データが読み取れる状態になったら教えて」を意味します。受付用のソケット（`listen`状態のソケット）にとっての「読み取れるデータ」とは、文字のメッセージではなく「新しいクライアントからの接続要求（新規着信）」のことです。

### 3. `listenPollFd.revents = 0;`

**【やっていること】OSからの「報告用スペース」をリセットする**

* `revents` (Returned Events) は、私たちが設定する項目ではなく、実際に `poll()` を実行した後に**OSが「結果」を書き込んで返してくれるための空欄**です。
* 監視を依頼する前（ `poll()` を呼ぶ前）なので、過去のゴミデータや誤動作を防ぐために、念のため `0`（ゼロ）で綺麗に初期化（リセット）して白紙の状態にしています。

### 4. `pollfds_.push_back(listenPollFd);`

**【やっていること】完成した依頼書を「監視リスト」に追加する**

* `pollfds_` は、すべての監視依頼書をまとめて管理するための可変長配列（`std::vector<struct pollfd>`）です。
* 記入が終わった依頼書（`listenPollFd`）を、このリストの最後（`push_back`）に追加して保管します。
* その後、メインループの中で `poll(&pollfds_[0], pollfds_.size(), -1)` と呼び出すことで、このリストに入っているすべての依頼書（最初は受付用ソケット1つだけですが、後からクライアントの専用ソケットも追加されていきます）が、束になって一斉にOSへ提出されます。

---

「依頼書を書き、空欄を作り、提出用のバインダー（ベクター）に綴じる」という、とても堅実で標準的な `poll` の初期化手順ですね。ここがしっかり書かれているからこそ、後の `while` ループで安全にクライアントを待ち受けることができています。
