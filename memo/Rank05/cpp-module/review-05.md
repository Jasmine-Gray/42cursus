### 1. アクセサーとミューテーターの違い

一般的に「アクセサー」と言うとゲッターとセッターの両方を指すことが多いですが、厳密なオブジェクト指向の用語では以下のように区別されます。

* **アクセサー（Accessor）**: オブジェクトの内部状態を取得するメソッド（＝**ゲッター**）
* **ミューテーター（Mutator）**: オブジェクトの内部状態を変更するメソッド（＝**セッター**）

今回のSubjectには "There are accessors for the attributes" と書かれており、別の箇所では明確に "You will provide getters for both attributes: getName() and getGrade()." と指定されています。

### 2. なぜセッター（Mutator）を作ってはいけないのか

今回の `Bureaucrat` クラスでは、以下の理由から汎用的なセッター（例: `setName()` や `setGrade()`）を実装すべきではありません。

* **`name` は定数であるため:**
Subjectには "A constant name." と明記されています。`const` なメンバ変数は、インスタンス化時（コンストラクタの初期化リスト）に一度だけ値を入れることができ、その後は変更不可能です。したがって、構造的にセッターを作ることはC++の文法上不可能です。


* **`grade` の変更ルールが厳格に決まっているため:**
グレードの値を変更する手段として、Subjectは任意の値を代入できる `setGrade()` ではなく、"implement two member functions to increment or decrement the bureaucrat's grade."（グレードをインクリメントまたはデクリメントする2つのメンバ関数を実装する）と明確に指示しています。これにより、外部から不正な値を直接セットされるのを防ぎ、必ず $+1$ または $-1$ ずつ変更され、かつ範囲外（1〜150）になった場合は例外をスローする安全な設計（カプセル化）が実現できます。

### レビュー項目の意味：標準例外の継承

> *"The exceptions that are used inherit from std::exception, or from something derived from std::exception (i.e. they are catchable as std::exception & e)."*

この一文は、**「あなたが独自に作成するすべての例外クラスは、C++の標準ライブラリに用意されている `std::exception` クラス（またはその派生クラス）を親クラスとして継承しなければならない」** という厳格なルールを示しています。

#### なぜこのルールが必要なのか？

C++では、理論上は `throw 42;` のように整数を投げたり、`throw "Error";` のように単なる文字列を例外として投げたりすることも可能です。しかし、そのような実装をしてしまうと、エラーを捕まえる（catchする）側が「何型の例外が飛んでくるか分からない」という状態に陥ります。

Subjectの `ex00` には、以下の実装例が指定されています。

```cpp
try
{
    /* do some stuff with bureaucrats */
}
catch (std::exception & e)
{
    /* handle exception */
}

```

独自の例外（例えば `Bureaucrat::GradeTooHighException` など）を `std::exception` から継承させておくと、**オブジェクト指向の多態性（ポリモーフィズム）** が働きます。これにより、上記のように `catch (std::exception & e)` というたった一つのブロックで、あらゆる種類の例外を一括して安全に捕まえることができるようになるのです。

### 満たすべき実装のポイント

このレビュー項目をクリアするためには、例外クラスを以下のように実装する必要があります。

1. **`public std::exception` を継承する:**
クラスを定義する際、`std::exception` をパブリック継承します。
2. **`what()` 関数をオーバーライドする:**
エラーメッセージを返すために、親クラスで定義されている仮想関数 `virtual const char* what() const throw();` を上書きします。（※C++98規格の要件です）。

**実装イメージ（例）:**

```cpp
class GradeTooHighException : public std::exception {
public:
    virtual const char* what() const throw() {
        return "Bureaucrat grade is too high!";
    }
};

```

※例外クラスに関しては、例外的に Orthodox Canonical Form（デフォルトコンストラクタ、コピーコンストラクタ、代入演算子、デストラクタの4点セット）で設計しなくてもよい、という免除ルールがSubjectに記載されています。

### 2. 親クラスはC++独自の関数か？

> 親クラスはcpp独自の関数ですか？

惜しいです！ `std::exception` は「関数」ではなく、C++の標準ライブラリに最初から用意されている「クラス」です。

関数とクラスの違いを簡単に整理すると以下のようになります。

* **関数（Function）**: 何かの「処理」をまとめたもの。（例：`getName()` や `what()`）
* **クラス（Class）**: データ（変数）と、それに対する操作（関数）を一つにまとめた「設計図」。（例：`Bureaucrat` や `std::exception`）

### 3. なぜ子クラスだとわかるのか？なぜ継承できるのか？

> GradeToolHighExceeotionはどうして子クラスだとわかるのですか？また、親クラスを継承できるのはどうしてですか？

#### どうして子クラスだとわかるのか？

それは、C++の文法において **`:`（コロン）** が使われているからです。

```cpp
class 子クラス名 : アクセス指定子 親クラス名

```

コード内の `class GradeTooHighException : public std::exception` という書き方は、コンパイラに対して「`GradeTooHighException` というクラスを作ります。これは `std::exception` を親として（`public`の形で）引き継ぎますよ」と宣言するC++の絶対的なルール（構文）です。この `:` があることで、誰が見ても（コンパイラが見ても）子クラスであることがわかります。

#### なぜ親クラスを継承できるのか？

C++が「オブジェクト指向プログラミング（OOP）」という概念をサポートしている言語だからです。

C++モジュールの目的の一つは、このOOPを学ぶことです。OOPの三大要素の一つに「継承（Inheritance）」があり、あるクラス（親）の便利な機能を、別のクラス（子）に丸ごとコピーして再利用したり、自分専用に少しだけ改造したりできる仕組みが言語自体に組み込まれています。

今回のケースで言えば、親である `std::exception` には「エラーメッセージを扱うための基本的な仕組み」がすでに備わっています。それを継承し、`what()` というメンバ関数だけを「上書き（オーバーライド）」して独自のエラー文を返すように改造している、というわけです。

今のヘッダーファイルの実装は、C++の例外処理のベストプラクティスに沿っています。このまま `Bureaucrat.cpp` の実装を進めていってください！他に文法で気になる点があればいつでもどうぞ。

C++ Module 05の例外処理クラス（`GradeTooHighException` など）を実装する上で、この2行は非常に重要な意味を持っています。C++98規格の要件と、`std::exception` の仕組みが詰まった部分ですので、それぞれのキーワード（単語）ごとに分解して詳しく解説します。

```cpp
public:
    virtual const char* what() const throw();

```

### 1. `public:`

これは**アクセス指定子**と呼ばれます。
この記述より下にあるメンバ（変数や関数）は、クラスの外側（例えば `main.cpp` の `try-catch` ブロックの中など）から誰でも自由に呼び出せるようになります。エラーメッセージを取得する関数は外部から呼ばれる必要があるため、必ず `public` に配置します。

### 2. `virtual const char* what() const throw();` の分解

この1行は、親クラスである `std::exception` にあらかじめ定義されている関数を、自分のクラス用に上書き（オーバーライド）するための宣言です。Module 05の要件である「`std::exception & e` としてキャッチできるようにする」ために不可欠な記述です。

それぞれの単語の意味は以下の通りです。

#### `virtual`（仮想関数）

この関数が親クラス（`std::exception`）の関数を上書きするものであることを示します。
これをつけておくことで、`catch (std::exception & e)` のように親クラスの型でキャッチされた場合でも、親のデフォルトのメッセージではなく、**あなたが作成した子クラス独自の `what()` が正しく呼び出される**ようになります（これをポリモーフィズムと呼びます）。

#### `const char*`（戻り値の型）

この関数が返すデータの型です。
C++の `std::string` ではなく、C言語スタイルの文字列（変更不可能な文字の配列へのポインタ）を返します。例えば `"Bureaucrat grade is too high!"` という文字列リテラルをそのまま返すことができます。

#### `what()`（関数名）

エラーの詳細を文字列として返す関数の名前です。`std::exception` クラスの仕様としてこの名前が決められています。

#### `const`（メンバ関数の修飾子）

**「この関数を呼び出しても、クラス内のメンバ変数の状態を一切書き換えない」** というコンパイラへの約束です。
エラーメッセージを取得するだけの処理が、オブジェクトの中身を勝手に書き換えてしまうと困るため、この安全装置がついています。

#### `throw()`（例外指定 / Exception Specification）

**ここがC++98特有の非常に重要な文法です。**
関数の後ろにつく `throw(...)` は、「この関数が実行中に投げる可能性のある例外の種類」をコンパイラに知らせるためのものです。
カッコの中が空っぽの `throw()` は、**「この `what()` 関数自身は、絶対に新たな例外を投げない」** という強い保証を意味します。
エラーの内容を伝えようとしている `what()` 関数自体がエラーを起こして例外を投げてしまうと、プログラムが完全にパニック状態に陥ってしまうため、親クラスの `std::exception` でこのように設計されています。親クラスと同じ形にするため、上書きする側も必ずこの `throw()` をつける必要があります。。


ご共有いただいたフィードバックと、Subject（課題）の絶対遵守という方針、素晴らしい心構えです。メンバ変数の命名（`_name` ではなく `name` にする）、RAIIの活用によるリソース管理、`// fallthrough` の明示、そしてストリーム状態ビットの確認など、いただいたフィードバック内容はすべて今後のC++プログラミングにおいて非常に重要かつ実践的なスキルです。これらをしっかりと念頭に置いて進めていきましょう。

さて、ご質問の「アクセス指定子が `private` なときはどんなことが起こるか」について解説します。

クラスのメンバ（変数や関数）を `private` に指定すると、主に以下の3つのことが起こります。

### 1. クラスの「外側」からのアクセスが完全に遮断される

`private` に指定されたメンバは、そのクラス自身のメンバ関数の中からしか読み書きできなくなります。もし、`main` 関数などクラスの外側から直接アクセスしようとすると、**コンパイルエラー**になります。

```cpp
class Bureaucrat {
private:
    std::string name; // privateなメンバ変数
};

int main() {
    Bureaucrat john;
    // john.name = "John"; // ← クラス外からのアクセスなのでコンパイルエラーになる！
}

```

### 2. 派生クラス（子クラス）からも直接アクセスできない

`protected` との最大の違いはここです。`private` なメンバは、そのクラスを継承した子クラスからであっても直接触ることはできません。
例えば、Module 05の Exercise 01 で作成する `Form` クラスでは、「これらの属性はすべて `private` であり、`protected` ではない（All these attributes are private, not protected.）」と厳密に指定されています。
そのため、後続のエクササイズで `Form` を継承して別の書類クラスを作ったとしても、子クラスは親クラスの `name` や `grade` を直接書き換えることはできず、親クラスが提供するパブリックなゲッター（`getName()` など）を経由して値を取得するしかありません。

### 3. クラスの安全性が保たれる（カプセル化）

これが `private` を使う最大の目的です。
変数を `private` に隠すことで、外部から「ありえない値」を勝手に代入される事故を防ぐことができます。

Module 05の `Bureaucrat` クラスを例に挙げます。
官僚のグレードは1から150までと決まっており、範囲外になったら例外（Exception）を投げる必要があります。もし `grade` が `public` だったら、誰でも `john.grade = -999;` のように直接無効な数値を代入できてしまいます。

`grade` を `private` に隠し、代わりに `incrementGrade()` や `decrementGrade()` といった `public` な関数だけを公開することで、「必ずチェック処理を通ってから値が変更される」という安全な設計（カプセル化）を強制できるのです。

### 1. `virtual const char* what() const throw();` の本当の意味

この行は関数が「どう振る舞うか」を宣言しているだけで、ここで例外を投げているわけではありません。単語ごとに分解すると以下のようになります。

* **`virtual`**: 仮想関数。親クラス（`std::exception`）の関数をオーバーライド（上書き）して、独自のエラーメッセージを返せるようにします。
* **`const char*`**: 関数の戻り値の型です。C言語スタイルの文字列（変更不可能な文字配列へのポインタ）を返します。
* **`what()`**: 関数名です。
* **`const`**: 「この関数を呼び出しても、クラス内部のメンバ変数は一切書き換えない」という保証です。
* **`throw()`**: **ここが最大の誤解ポイントです。** これは「例外を投げる」という意味ではなく、C++98規格の「例外指定」という構文で、カッコの中が空っぽであることは **「この `what()` 関数自身は、絶対に例外を投げない（無例外保証）」** ということをコンパイラに約束するものです。

### 2. 例外発生から出力までの正しいフロー

実際に例外が発生して画面に文字が出るまでは、以下のような順番で処理が進みます。

#### ステップ 1: 例外の発生（トリガー）

例外のトリガーは `what()` ではなく、プログラマが明示的に書く **`throw` キーワード** です。ここで自作の例外クラスのオブジェクトを投げます。

```cpp
void Bureaucrat::incrementGrade() {
    if (grade <= 1) {
        // ここがトリガー！例外オブジェクトを作って投げる
        throw Bureaucrat::GradeTooHighException();
    }
    // ...
}

```

#### ステップ 2: 例外の捕捉（キャッチ）

投げられた例外は、関数をさかのぼり、`try-catch` ブロックの **`catch`** に捕まります。

```cpp
try {
    john.incrementGrade();
}
catch (std::exception & e) { // ここで捕まえる[cite: 7]
    // 次のステップへ
}

```

#### ステップ 3: `what()` の呼び出しと出力

`catch` ブロックの中に入って初めて、プログラマが手動で `e.what()` を呼び出します。
`what()` は単に `"Bureaucrat grade is too high!"` という文字列（`const char*`）を返す**だけの関数**です。自動的に標準出力には出ないため、`std::cout` や `std::cerr` を使って自分で出力する必要があります。

```cpp
catch (std::exception & e) {
    // e.what() が文字列を返し、それを std::cerr に渡すことで初めて画面に出る
    std::cerr << "Exception: " << e.what() << std::endl;
}

```

### まとめ

* `throw` キーワードによって例外が投げられ、それを `catch` したあとに、エラー理由の文字列をもらうために `what()` を呼び出し、手動で `std::cerr` などに出力する。
* **`throw()` の意味:** 「この `what()` 関数の中では絶対にエラー（例外）を起こしません」というC++98特有の安全宣言。

### 1. `e.what()` とは何か？

`e.what()` は、「起きたエラー（例外）の具体的な内容を、文字列として教えてくれる関数」です。

* **仕組み**: `std::exception` クラス（およびそれを継承したすべての標準例外クラス）には、`what()` というメンバ関数があらかじめ用意されています。
* **戻り値**: この関数を呼び出すと、エラーの理由を説明するC言語スタイルの文字列（`const char*`型）が返ってきます。
* **使い方**: 例えば、`try` ブロックの中でエラーが起きて例外が投げられたとき、`catch` ブロック内で `std::cerr << e.what() << std::endl;` のように記述することで、「何が原因で処理が失敗したのか」を画面に表示させることができます。自作の例外クラスを作った場合は、この `what()` をオーバーライド（上書き）して、独自のエラーメッセージを返すように実装します。

### 2. `std::exception& e` の `e` の意味と役割は何か？

ここでの `e` は、「キャッチした例外オブジェクトそのものにアクセスするための変数名（参照）」です。

* **`e` の意味**: 単なる変数名です。「exception」の頭文字を取って `e` と命名するのがC++の慣習になっています（`ex` と書く人もいます）。
* **`&`（参照）の役割**: ここが非常に重要です。`catch (std::exception e)` のように値渡し（コピー）で受け取るのではなく、必ず `&` をつけて**参照渡し**で受け取ります。
* もしコピーで受け取ってしまうと、子クラス（例：`GradeTooHighException`）として投げられた例外が、親クラス（`std::exception`）の型に無理やり変換されて切り詰められてしまう「オブジェクトスライシング」という現象が起きます。
* 参照（`&`）で受け取ることで、元の「子クラスの例外オブジェクト」の正体を保ったままキャッチでき、`e.what()` を呼んだときに親クラスのデフォルトメッセージではなく、**子クラスで設定した独自のエラーメッセージ**を正しく呼び出すことができます（ポリモーフィズム）。



### 3. `throw()` の意味（C++98の安全宣言）について

関数名の後ろにつける `throw()` は、「この関数の中では、いかなる例外（エラー）も外に向かって投げません」というコンパイラへの絶対的な約束です。

* **なぜこの宣言が必要なのか？**
例外処理の最中（すでにエラーが起きて `catch` を探しているパニック状態のとき）に、エラーメッセージを取り出そうと `what()` を呼び出したとします。もしこの `what()` 関数自体が内部で新たなエラーを起こして例外を投げてしまうと、C++のシステムは「エラー処理中に別のエラーが起きた！」と判断し、安全のためにプログラムを強制終了（`std::terminate`）させてしまいます。
* **安全宣言としての役割**
プログラムの強制終了という最悪の事態を防ぐため、エラー情報を返す `what()` 関数や、オブジェクトを片付けるデストラクタなどは、「絶対に内部で例外を発生させない安全な関数」として設計されなければなりません。C++98では、その「絶対に例外を投げない」という仕様を明示する文法が、カッコの中身が空っぽの `throw()` なのです。

*(補足: C++11以降ではこの `throw()` は非推奨となり `noexcept` というキーワードに置き換わりましたが、Subjectの指定によりC++98規格でコーディングする必要があるため、Module 05では `throw()` を使うのが正解です)*

### 1. 求められている機能

通常、C++では `std::cout << bureaucrat_instance;` のように自作クラスのオブジェクトをそのまま出力しようとするとコンパイルエラーになります。これを可能にするために、`std::ostream` に対する `<<` 演算子の働きを独自に定義（オーバーロード）する必要があります。

### 2. 指定された出力フォーマットの厳守

課題（Subject）には、出力フォーマットが明確に指定されています。
`<name>, bureaucrat grade <grade>.`


（※ `< >` の記号自体は出力せず、実際の名前とグレードの数値に置き換え、最後にピリオド `.` をつけます。）

### 3. 実装上の最重要注意点（ルールの遵守）

ここが最もつまずきやすいポイントですが、以下のModule共通ルールを守る必要があります。

* **`friend` キーワードの禁止:** Subjectで明記されていない限り、`friend` キーワードの使用は禁止されています（使用すると評価が-42点になります）。


* **Getterの活用:** したがって、この `<<` 演算子のオーバーロード関数は `Bureaucrat` クラスのメンバ関数や `friend` 関数としては定義できません。クラスの**外部の関数**として定義し、カプセル化されたプライベートメンバ（フィードバック通り `_name` ではなく `name`）の値を取得するために、必ずパブリックなゲッター（`getName()` や `getGrade()`）を使用する必要があります。



### 実装イメージ

**ヘッダーファイル (`Bureaucrat.hpp`)**
クラス定義の「外側」にプロトタイプ宣言を記述します。

```cpp
class Bureaucrat {
    // ... クラスの実装 ...
};

// クラスの外に記述
std::ostream& operator<<(std::ostream& os, const Bureaucrat& bureaucrat);

```

**ソースファイル (`Bureaucrat.cpp`)**
ゲッターを経由して指定フォーマット通りにストリーム（`os`）に流し込みます。

```cpp
std::ostream& operator<<(std::ostream& os, const Bureaucrat& bureaucrat) {
    os << bureaucrat.getName() << ", bureaucrat grade " << bureaucrat.getGrade() << ".";
    return os;
}

```

このように実装することで、指定されたレビュー項目を完全に満たしつつ、Subjectの禁止事項（`friend` の使用）にも抵触しない安全なコードになります。


### 1. 左辺のオペランド（被演算子）のルール

C++において、二項演算子（左右に値を取る演算子）を「クラスのメンバ関数」としてオーバーロードする場合、**左辺にあるオブジェクトがそのクラス自身のインスタンス（`this`）でなければならない**という文法上の絶対的なルールがあります。

私たちが普段 `<<` 演算子を使うときの形を思い浮かべてみてください。

`std::cout << bureaucrat;`

この場合、演算子の左辺にあるのは `Bureaucrat` クラスのオブジェクトではなく、`std::ostream` クラスのオブジェクトである `std::cout` です。

### 2. もしメンバ関数として定義してしまったら？

もし `Bureaucrat` クラスのメンバ関数として `operator<<` を定義した場合、左辺に `Bureaucrat` のオブジェクトを置かなければ関数を呼び出すことができなくなります。つまり、出力を行うために以下のような不自然な書き方をしなければならなくなります。

`bureaucrat << std::cout;`

これはC++の標準的な出力の直感に完全に反しており、`std::cout << obj1 << obj2;` のように `<<` を連続して繋げる（チェーンする）使い方もできなくなってしまいます。

### 3. クラスの外部（非メンバ関数）で定義する正しいアプローチ

左辺に `std::ostream`（`std::cout` など）、右辺に `Bureaucrat` オブジェクトを置くという自然な形を実現するためには、この演算子オーバーロードをクラスのメンバ関数ではなく、外部の関数（非メンバ関数）として定義する必要があります。

```cpp
// クラスの外部に定義する
std::ostream& operator<<(std::ostream& os, const Bureaucrat& obj) {
    os << obj.getName() << ", bureaucrat grade " << obj.getGrade() << ".";
    return os;
}

```

このように、第一引数に左辺の `std::ostream&`、第二引数に右辺の `const Bureaucrat&` を受け取るように設計することで、私たちがよく知る自然な構文で出力できるようになります。

### 4. Subjectのルールとカプセル化の維持

ここで重要になるのが、提供されているSubjectのルールです。クラス外部の関数からクラスの `private` なメンバ変数に直接アクセスするために `friend` キーワードを使うアプローチがC++にはありますが、今回の課題では明確に指定されていない限り `friend` キーワードの使用は禁止されています（使用すると -42点になります）。

そのため、この非メンバ関数の中で `Bureaucrat` の情報（名前やグレード）を出力するには、メンバ変数を `private` のまま保ちつつ、必ずパブリックなゲッター（`getName()` や `getGrade()`）を経由して値を取得する設計にしなければなりません。これが、要件を満たしつつカプセル化を守るための正しいアプローチです。
