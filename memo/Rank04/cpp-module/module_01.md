### 1. Stack領域：「作業用の小さな机」

スタックは、関数の中のローカル変数などを一時的に置いておくための領域です。

* **特徴:**
  * **超高速:** メモリの確保と解放が一瞬で終わります。
  * **自動管理:** 関数やスコープ（`{ }` の中）が終わると、**自動的にデータが消去（デストラクタが実行）**されます。
  * **LIFO（後入れ先出し）:** 本を積み上げるようにデータが置かれ、上から順番に片付けられます。
  * **容量が小さい:** 大きなデータ（巨大な配列など）を置くと「スタックオーバーフロー」を起こしてプログラムがクラッシュします。
* **C++での書き方（newを使わない）:**
  ```cpp
  void doSomething() {
      Zombie myZombie("StackZom"); // スタックに確保
      myZombie.announce();
  } // ← 関数が終わるこの瞬間に、自動で myZombie が破壊（delete）される！
  ```

### 2. Heap領域：「巨大な貸し倉庫」

ヒープは、プログラムの実行中に「必要な時に、必要なだけ」場所を借りてデータを置いておくための広大な領域です。（動的メモリ割り当てと呼びます）
これまでのExercise 02と03を通じて学んだ、C++における「参照（Reference）」と「ポインタ（Pointer）」の核心となる違いと使い分けについて、この課題の文脈に沿って総まとめします！

ここを理解できたことは、C++プログラマとして最初の大きな山を越えたことを意味します。

### 🤝 2つの共通点：どちらも「原本」を扱っている
まず大前提として、参照もポインタも**「値のコピー（値渡し）を防ぎ、大元のデータ（原本）を共有する」**という目的は全く同じです。
だからこそ、大元の武器の名前を変えたとき、BobもJimも新しい武器の名前で攻撃できました。

---

### 🔗 参照（Reference / `HumanA`）のポイント
**「絶対に必要で、一生変わらない関係」**を表すのに使います。見えない頑丈な糸で結ばれているイメージです。

1. **絶対に `NULL` にならない（安全）**
   * 「武器を持たない人間」というバグが起きる余地が文法レベルで排除されています。
2. **生まれた瞬間に結びつける必要がある（必須）**
   * コンストラクタの**初期化子リスト（`: weapon(weapon)`）**を使って、誕生と同時にリンクさせなければコンパイルエラーになります。
3. **途中で対象を変えられない（固定）**
   * 一度 `club` と結びついたら、後から別の武器（例えば `sword`）に結び直すことはできません。

### 📍 ポインタ（Pointer / `HumanB`）のポイント
**「なくてもいいし、後から変えてもいい関係」**を表すのに使います。住所を書き込める手帳（メモ帳）のイメージです。

1. **`NULL`（空っぽ）を許容できる（任意）**
   * コンストラクタで `NULL` を入れておくことで、「最初は手ぶらで誕生する」という状態を自然に表現できます。
2. **後から対象を変更できる（柔軟）**
   * `setWeapon` を使って、手帳の住所を書き換えることで、途中で別の武器に持ち替える（装備する）ことができます。
3. **使う時は中身の確認が必要（自己責任）**
   * 住所が空っぽ（`NULL`）のままアクセスするとプログラムがクラッシュするため、`if (_weapon)` のように「持っているか？」の確認をする責任が伴います。

---

### 📊 比較まとめ表

| 特徴 | 参照（`Weapon&` / HumanA） | ポインタ（`Weapon*` / HumanB） |
| :--- | :--- | :--- |
| **関係性のイメージ** | 見えない頑丈な糸（エイリアス） | 住所を書いた手帳（メモ） |
| **未装備（`NULL`）** | ❌ できない（絶対持っている） | ⭕️ できる（手ぶらOK） |
| **途中で持ち替え** | ❌ できない（一生同じ武器） | ⭕️ できる（後から変更可能） |
| **初期化のタイミング** | コンストラクタ（初期化子リスト） | いつでもOK（最初はNULLも可） |
| **アクセス方法** | `weapon.getType()`（普通と同じ） | `weapon->getType()`（矢印が必要） |

C++の設計では、**「基本は安全で高速な『参照』を使い、どうしてもNULLや変更が必要な場面だけ『ポインタ』を使う」**というのがプロの鉄則（ベストプラクティス）です。今回の課題は、まさにその使い分けを体感するための最高の題材でした。

ポインタと参照のモヤモヤ、これで完全に晴れましたでしょうか？
準備ができたら、いよいよファイルの読み書きと文字列置換を行う **Exercise 04: Sed is for losers** に挑みましょうか！
* **特徴:**
  * **広大:** メモリの許す限り、巨大なデータを保存できます。
  * **手動管理:** プログラマが**「ここで場所を借りる（`new`）」「ここで返す（`delete`）」**と明示的に指示しなければなりません。
  * **生存期間が自由:** 関数が終わっても、`delete` されるまではデータが生き残ります（他の関数へデータを渡す時に便利です）。
  * **少し遅い:** 空いている場所を探して確保するため、スタックより処理に時間がかかります。
  * **メモリリークの危険:** 借りた場所を `delete` で返し忘れると、永遠にメモリが占有されたままになり（メモリリーク）、いずれコンピュータがパンクします。
* **C++での書き方（newを使う）:**
  ```cpp
  Zombie* createZombie() {
      Zombie* heapZom = new Zombie("HeapZom"); // ヒープに確保（ポインタで受け取る）
      heapZom->announce();
      return heapZom; // 関数が終わっても破壊されない！
  }

  void play() {
      Zombie* z = createZombie();
      // ... 色々遊ぶ ...
      delete z; // ← 自分で忘れずに破壊（解放）しなければならない！
  }
  ```

## ex00: BraiiiiiiinnnzzzZ


### new失敗時の挙動
結論から言うと、C++の `new` 演算子がメモリの確保に失敗した場合（例えば、コンピュータのメモリが完全に枯渇してしまった場合など）、**`NULL` を返すのではなく、「例外（Exception）」というものを投げてプログラムを強制終了させます。**

---


### 1. 無意味なエラーチェック

C言語では、`malloc` が失敗すると `NULL` を返してくれたため、以下のようにチェックするのが常識でしたよね。

```c
// C言語の常識（malloc）
Zombie* z = (Zombie*)malloc(sizeof(Zombie));
if (z == NULL) {
    printf("メモリ確保失敗！\n");
    return;
}
```

これをC++に持ち込んで、以下のように書いてしまう人が非常に多い。

```cpp
// ❌ C++では意味のないエラーチェック
Zombie* z = new Zombie("Foo");
if (z == NULL) {  // ← ここには永遠に到達しない！
    std::cout << "メモリ確保失敗！" << std::endl;
}
```

**`new` は失敗した瞬間に `std::bad_alloc` という「例外（エラーの爆弾のようなもの）」を爆発させ、その時点でプログラムの処理を強制的に中断して吹っ飛んでしまう**。そのため、その下の `if (z == NULL)` の行が実行されることは絶対にありません。

### 2. 正しい対処法①：`try-catch` を使う（C++の正攻法）

C++で `new` の失敗を安全にキャッチ（捕捉）するには、例外処理専用の構文である `try-catch` ブロックを使います（これは後の Module 05 あたりで本格的に学びます）。

```cpp
#include <iostream>
#include <new> // std::bad_alloc を使うために必要

try {
    // 爆発するかもしれない危険な処理を try で囲む
    Zombie* z = new Zombie("Foo"); 
    // ... 成功した時の処理 ...
} 
catch (const std::bad_alloc& e) {
    // もし new が失敗（爆発）したら、ここでキャッチして安全に処理する
    std::cout << "メモリ確保に失敗しました: " << e.what() << std::endl;
}
```

### 3. 正しい対処法②：`malloc` のように `NULL` を返させる裏技

「例外とかよく分からないから、C言語みたいに `NULL` を返すようにしてほしい！」という場合のために、`std::nothrow` というオプションも用意されています。

```cpp
#include <new> // std::nothrow に必要

// (std::nothrow) をつけると、失敗時に爆発せず NULL を返すようになる
Zombie* z = new (std::nothrow) Zombie("Foo");

if (z == NULL) {
    std::cout << "メモリ確保失敗！（安全に検知）" << std::endl;
}
```

「`new` は失敗すると `NULL` ではなく例外を投げる」

## ⚠new 注意点
---

### 鉄則1：`new` したら必ず `delete` する（メモリリークの防止）

`new` を使ってヒープ領域に確保したメモリは、プログラムが終了するまで（あるいはOSが強制終了させるまで）**永遠に残り続けます**。

* **注意点:** 使い終わったのに `delete` を忘れると、メモリが徐々に圧迫されていく**「メモリリーク（Memory Leak）」**が発生します。
* **対策:** `new` を書いたら、必ずセットで `delete` を書く場所を設計段階で決めておくこと。

```cpp
void badFunction() {
    Zombie* z = new Zombie("Foo");
    z->announce();
    // ❌ delete z; を書き忘れている！この関数が終わると、
    // ポインタ 'z' は消えるのに、ヒープ上のゾンビ本体は永遠に残り続ける（迷子になる）。
}
```

### 鉄則2：配列を `new` したら `delete[]` を使う（ex01の超重要ポイント）

まさに次に取り組む **Exercise 01 (zombieHorde)** で必要になる知識です。
単体のオブジェクトではなく、**配列**としてメモリを確保した場合、消し方が変わります。

* **注意点:** `new[]` で作ったものを普通の `delete` で消すと、**最初の1つ目しかデストラクタが呼ばれず、残りがすべてメモリリーク**します。

```cpp
// ⭕️ 正しい配列の作り方と消し方
Zombie* horde = new Zombie[10]; // 10体分の配列を作る

// ... 遊び終わったら ...

delete[] horde; // ⭕️ 配列用の delete[] を使う！10体すべてが破壊される
// delete horde; // ❌ 絶対ダメ！1体目しか破壊されない
```

### 鉄則3：破壊した後のポインタは `NULL` にする（ダングリングポインタ対策）

個人的に一番ハマりやすいのがこれです。
`delete ptr;` を実行すると、メモリ上のデータ（ゾンビ本体）は破壊されますが、**`ptr` という変数の中には「破壊された場所の古い住所」がそのまま残ってしまいます。** これを「ダングリングポインタ（宙吊りポインタ）」と呼びます。

* **注意点:** 破壊済みの住所にアクセスしようとすると、プログラムがクラッシュ（セグフォ）します。
* **対策:** `delete` したら、すかさず `NULL`（無効な住所）を代入してリセットする癖をつけます。

```cpp
Zombie* z = new Zombie("Foo");
delete z; // ゾンビ本体を破壊！

// ❌ 危険：z の中にはまだ住所が残っている
// z->announce(); // ← クラッシュする！(Use after free)

// ⭕️ 安全：NULL を入れておく
z = NULL;
```

### 鉄則4：二重解放（Double Free）は即クラッシュ

同じメモリ領域を**2回 `delete` してしまう**と、C++では重大なエラーとなりプログラムが即座に強制終了します。

しかし、鉄則3で紹介した **`NULL` を代入するテクニック**を使っていれば、これを完全に防ぐことができます。なぜなら、C++の仕様で**「`NULL` に対する `delete` は何も起きない（安全に無視される）」**と決まっているからです。

```cpp
Zombie* z = new Zombie("Foo");
delete z;
z = NULL; // ここで NULL にしておく

delete z; // ⭕️ NULLをdeleteしても何も起きないので、二重解放でクラッシュしない！安全！
```

---

### まとめ

1. **`new`** と **`delete`** は一生のペア。
2. **`new[]`** には **`delete[]`** を合わせる。
3. `delete` した直後に **`ptr = NULL;`** と書く癖をつける。

（※C++11以降では `NULL` の代わりに `nullptr` を使うのが常識ですが、42の課題は C++98 縛りなので `NULL` を使います）

## ex01: Moar brainz!


`delete[] horde;` を実行した瞬間、プログラムは配列の中にある **N個すべてのゾンビのデストラクタを自動的にN回呼び出します。**

### 1. 破壊は「逆順」で行われる
`new[]` で配列を作った時、コンストラクタは 0番目、1番目、2番目... と順番に呼ばれました。
しかし `delete[]` を実行すると、デストラクタは **一番最後（N-1番目）から、0番目に向かって逆順で呼ばれていきます。**

もしN=5でテストを実行すると、ターミナルの出力はこうなるはずです。
```text
Zombie [4] is destroyed...
Zombie [3] is destroyed...
Zombie [2] is destroyed...
Zombie [1] is destroyed...
Zombie [0] is destroyed...
```
（C++では「後から作られたものほど先に片付ける（LIFO）」という設計思想があるためです）

### 2. コンパイラはどうやって「N回」だと知っているのか？

 `new Zombie[5]` を実行した時、C++はメモリを確保する際、**私たちが使える配列の「すぐ手前の秘密の場所」に、こっそり「この配列は5個入りだよ」というメモを隠し持っている**のです。
`delete[]` はその秘密のメモを読み取って、「なるほど、5回デストラクタを呼べばいいんだな」と判断しています。

### 3. だから `[]` を忘れると大惨事になる
もし間違えて普通の `delete horde;` と書いてしまうと、コンパイラに「これはただの単体（1個）のゾンビです」と嘘をつくことになります。

その結果、コンパイラは秘密のメモを読まず、**0番目のゾンビのデストラクタだけを1回呼んで、残りの4体の破壊をサボってしまいます。** これが、先ほどお話しした「配列のメモリリーク」の正体です。

## ex02: HI THIS IS BRAIN

---
###  ポインタ (`*`) と 参照 (`&`) の決定的な違い

**参照はポインタの「危険な部分」を取り除いた、安全で使いやすい別名（エイリアス）**なのです。


| 特徴 | ポインタ (`*`) | 参照 (`&`) |
| :--- | :--- | :--- |
| **`NULL` の代入** | ⭕️ できる（空っぽの住所を持てる） | ❌ **絶対にできない**（必ず実体が必要） |
| **途中で対象を変更** | ⭕️ できる（別の住所に書き換え可能） | ❌ **絶対にできない**（一度決めたら一生同じものを指す） |
| **使う時の構文** | `*ptr` や `ptr->` など、記号が必要 | `ref` のように、**普通の変数と全く同じ書き方で使える** |

前回のゾンビの課題で「`NULL` チェック」や「`->`（アロー演算子）」を使いましたが、参照を使えばそういった面倒な処理やクラッシュの危険を大幅に減らすことができます。

---


### 1. 値渡し（Pass by Value）＝「コピーを渡す」

あなたが「企画書（データ）」を持っていて、同僚に「これ、チェックしておいて」と渡す場面を想像してください。

「値渡し」は、**原本をコピー機で印刷して、そのコピーを相手に渡す**行為です。
* **メリット:** 相手がコーヒーをこぼしたり、勝手に落書き（データの書き換え）をしても、あなたの手元にある原本は絶対に安全です。
* **デメリット:** 毎回コピー機を通すので「時間」がかかり、紙（メモリ）を無駄に消費します。もし企画書が1万ページ（巨大なデータ）だったら最悪ですよね。

```cpp
// 【値渡し】コピーが渡される
void addBacon(std::string burger) {
    burger += " with Bacon"; // コピーにベーコンを追加
}

int main() {
    std::string myLunch = "Hamburger";
    addBacon(myLunch);
    // myLunch の中身は "Hamburger" のまま！（原本は変わらない）
}
```

### 2. 参照渡し（Pass by Reference）＝「GoogleドキュメントのURLを共有する」

一方「参照渡し」は、紙ではなく**「Googleドキュメント（クラウド上の原本）の共有リンク」を相手に教える**行為です。

* **メリット:** 1万ページの書類でも、リンク（参照）を教えるだけなので一瞬で渡せます（メモリの節約・爆速）。
* **デメリット（特徴）:** 相手がそのリンクを開いて文章を書き換えると、**あなたの画面の原本もリアルタイムで書き換わります。** なぜなら、見ている実体（原本）が全く同じだからです。

```cpp
// 【参照渡し】名前の後に「&」をつけるだけ！原本が共有される
void addBacon(std::string& burger) {
    burger += " with Bacon"; // 原本に直接ベーコンを追加！
}

int main() {
    std::string myLunch = "Hamburger";
    addBacon(myLunch);
    // myLunch の中身が "Hamburger with Bacon" に変わっている！
}
```

### 3. なぜ「ポインタ渡し」を使わないの？

「原本を直接書き換えるなら、C言語でやったポインタ（`*`）を使えばいいのでは？」と思うかもしれません。確かにポインタでも全く同じことができます。

```cpp
// 【ポインタ渡し】（C言語のやり方）
void addBacon(std::string* burger) {
    if (burger != NULL) { // 常にNULLチェックが必要！
        *burger += " with Bacon"; // 毎回「*」をつけて中身を取り出さないといけない
    }
}
```

しかし、ポインタは「NULLが渡されるかもしれない」「間違えて別の住所に書き換えてしまうかもしれない」という危険性があり、いちいち `*` や `->` を書くのが面倒です。

そこでC++は**「ポインタのように『原本』を共有できるけど、NULLになる危険性がなく、普通の変数と全く同じ書き方（`*`が不要）で安全に扱える魔法の別名」**を作りました。それが**参照（`&`）**なのです。

| 特徴 | 参照（`Weapon&` / HumanA） | ポインタ（`Weapon*` / HumanB） |
| :--- | :--- | :--- |
| **関係性のイメージ** | 見えない頑丈な糸（エイリアス） | 住所を書いた手帳（メモ） |
| **未装備（`NULL`）** | ❌ できない（絶対持っている） | ⭕️ できる（手ぶらOK） |
| **途中で持ち替え** | ❌ できない（一生同じ武器） | ⭕️ できる（後から変更可能） |
| **初期化のタイミング** | コンストラクタ（初期化子リスト） | いつでもOK（最初はNULLも可） |
| **アクセス方法** | `weapon.getType()`（普通と同じ） | `weapon->getType()`（矢印が必要） |

C++の設計では、**「基本は安全で高速な『参照』を使い、どうしてもNULLや変更が必要な場面だけ『ポインタ』を使う」**というのがプロの鉄則（ベストプラクティス）。

---

### 1. スコープ (Scope) ＝「変数が生きられる部屋」

スコープとは、変数が「存在できる範囲」と「寿命」を決めるルールです。C++では、**中括弧 `{ }` で囲まれた範囲が1つのスコープ（部屋）**になります。

* **ルール:** `{` で部屋に入り、その中で作られた変数は、**部屋の出口である `}` に到達した瞬間に、例外なくすべて抹殺（破棄）されます。**

```cpp
int main() {
    // 部屋の外
    { // 👈 スコープ（部屋）の入り口
        std::string name = "Bob"; // Bob誕生

    } // 👈 スコープの出口！ ここで Bob は自動的に破壊される！

    // std::cout << name; // ❌ エラー！Bobはもうこの世に存在しない
}
```
この「スコープを抜けると自動で破棄される」という仕組みのおかげで、私たちはスタックメモリ（普通の変数）のメモリリークを気にせずにプログラムを書くことができます。

---

### 2. コンストラクタ (Constructor) ＝「誕生の瞬間の『準備』」

コンストラクタは、オブジェクト（クラスから作られた実体）が**スコープの中で「生まれた瞬間」に、一番最初に自動で呼ばれる特別な関数**です。

* **特徴:** 必ず「クラスと同じ名前」で、戻り値（`void` など）はありません。
* **役割:** オブジェクトが正しく生きるための初期設定（名前をつける、武器を持たせる、必要なメモリを確保するなど）を行います。

```cpp
class Human {
public:
    // 👈 これがコンストラクタ！生まれた瞬間に呼ばれる
    Human(std::string name) {
        std::cout << name << " が誕生した！" << std::endl;
    }
};

int main() {
    Human bob("Bob"); // ここで自動的にコンストラクタが呼ばれる！
}
```
**★ポイント:** 前回の `HumanA` のように「初期化子リスト（`: weapon(weapon)`）」を使うと、生まれた瞬間に「必ず持っていなければならないもの（参照）」をガッチリとセットすることができます。

---

### 3. デストラクタ (Destructor) ＝「死ぬ瞬間の『後片付け』」

デストラクタは、オブジェクトが**「死ぬ（破壊される）瞬間」に、最後に自動で呼ばれる特別な関数**です。

* **特徴:** 必ずクラス名の前にチルダ `~` がつきます（例：`~Human()`）。引数は受け取れません。
* **役割:** オブジェクトが死ぬ前に、使っていたものを綺麗に片付けます（特に、`new` で借りたメモリを `delete` で返すなど）。
* **いつ呼ばれる？:** 1. オブジェクトが**スコープの出口 `}` に到達したとき**（スタック領域）。
    2. プログラマが手動で **`delete` を実行したとき**（ヒープ領域）。

```cpp
class Human {
public:
    Human() { std::cout << "誕生" << std::endl; }

    // 👈 これがデストラクタ！死ぬ瞬間に呼ばれる
    ~Human() { std::cout << "死亡と後片付け" << std::endl; }
};
```
**★ポイント:** スコープを抜ける時、デストラクタは**「後から生まれたものから順番に呼ばれる（LIFO）」**という絶対のルールがあります（ex01のゾンビ配列 `delete[]` で、N番目から0番目へ逆順に破壊されたのはこのルールのためです）。

### この3つがどう連動するのか

```cpp
class Box {
public:
    Box()  { std::cout << "箱を開けた！(コンストラクタ)" << std::endl; }
    ~Box() { std::cout << "箱を捨てた！(デストラクタ)" << std::endl; }
};

int main() {
    std::cout << "--- 部屋に入る ---" << std::endl;
    { // スコープの始まり
        Box myBox; // ここで「箱を開けた！」が出力される

        std::cout << "部屋の中で遊んでいる..." << std::endl;

    } // スコープの終わり！ここで自動的に「箱を捨てた！」が出力される
    std::cout << "--- 部屋から出た ---" << std::endl;
}
```

**【実行結果】**
```text
--- 部屋に入る ---
箱を開けた！(コンストラクタ)
部屋の中で遊んでいる...
箱を捨てた！(デストラクタ)
--- 部屋から出た ---
```

コンストラクタで準備し、スコープの中で活動し、スコープから出る瞬間にデストラクタで片付ける。
