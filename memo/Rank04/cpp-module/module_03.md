### 1. 継承 (Inheritance) について

継承とは、**「すでに存在するクラス（親）のデータや機能を、新しいクラス（子）がそのまま引き継いで使う」**仕組みです。

* **親クラス（Base class）**: 基礎となる設計図。例：`ClapTrap`
* **子クラス（Derived class）**: 親の性質を受け継ぎつつ、新しい特徴を追加した設計図。例：`ScavTrap`, `FragTrap`

#### 💡 継承の最大のメリット：コードの再利用
もし継承がなかったら、`ScavTrap` を作る際にもう一度 `hitPoints` や `takeDamage` のロジックをゼロから書き直さなければなりません。継承を使うことで、**「共通部分は親に任せて、子は自分だけの特別な機能（`guardGate` など）を作ることに専念できる」**ようになります。

#### ⚠️ コードを書くときの重要視点（注意点）

継承を使う際は、以下の3点に特に注意して設計する必要があります。

1.  **アクセス修飾子 (`private` と `protected` の違い)**
    * 親クラスの変数が `private` だと、いくら血の繋がった子クラスであっても直接アクセスできません。
    * 子クラス（`ScavTrap`など）から親クラスの変数（`name` や `hitPoints`）を直接いじりたい場合は、親クラス側でアクセス権を **`protected`** に設定する必要があります。<br>
		```protectedは、クラスメンバー（変数や関数）に対するアクセス指定子の一つで、定義したクラス自身と、それを継承した派生クラス内からはアクセス可能、外部（インスタンスなど）からはアクセス不可にする機能です。カプセル化を維持しつつ、継承関係にあるクラス間でのみ情報を共有するために使用されます。```
2.  **構築と破棄の順番（ライフサイクル）**
    * **生成時:** 必ず **「親 → 子」** の順番でコンストラクタが呼ばれます（土台がないと装飾できないため）。
    * **破棄時:** 必ず **「子 → 親」** の逆順でデストラクタが呼ばれます（RAIIの原則）。
3.  **多重継承の罠（菱形継承）**
    * `DiamondTrap` で経験したように、複数の親から継承すると、大元の親（`ClapTrap`）が重複して生成されてしまう問題（Diamond Problem）が起きます。これを防ぐためには `virtual public`（仮想継承）という特殊な書き方で、「親のインスタンスは1つだけ共有する」と明示する必要があります。

### 1. オーバーライドとは？

一言でいうと、**「親クラスから受け継いだ関数の処理を、子クラス専用の処理で『上書き（再定義）』すること」**です。

継承を使うと、親の機能をそのまま使えるというメリットがありますが、「基本機能は親のままでいいけど、**この機能だけは自分流にアレンジしたい！**」という場面が必ず出てきます。これを実現するのがオーバーライドです。

### 2. 具体例：`ScavTrap`の`attack`関数


#### 【親クラス】ClapTrap の attack
親である `ClapTrap` は、以下のような標準的な攻撃処理を持っていました。
```cpp
void ClapTrap::attack(const std::string& target) {
    // ...EP消費の処理...
    std::cout << "ClapTrap " << this->name << " attacks " << target 
              << ", causing " << this->attackDamage << " points of damage!" << std::endl;
}
```

#### 【子クラス】ScavTrap の attack （オーバーライド！）
しかし、`ScavTrap` は「自分はただのClapTrapとは違う、もっと凶悪なロボットだ！」という個性を持たせるようSubjectで指示されていました。そこで、**関数名と引数を全く同じにして**、新しい処理を書きました。

```cpp
void ScavTrap::attack(const std::string& target) {
    // ...EP消費の処理...
    std::cout << "ScavTrap " << this->name << " viciously attacks " << target 
              << ", causing " << this->attackDamage << " points of massive damage!" << std::endl;
}
```

このように実装することで、`ScavTrap` のインスタンスに対して `attack()` を呼んだ時は、親の地味な攻撃メッセージではなく、**子クラスで上書きした凶悪な攻撃メッセージが優先して実行**されます。

### 3. オーバーライドの厳格なルール

オーバーライドを成立させるためには、以下の条件を**完全に**満たす必要があります。

* **関数名が同じであること**
* **引数の「型」と「数」が完全に同じであること**
* **戻り値の型が同じであること**

先ほど解説した「オーバーロード（多重定義）」は引数が**違う**必要がありましたが、オーバーライドは引数まで**完全に一致**させなければなりません。もし引数を少しでも変えてしまうと、コンパイラは「あ、これは親の上書きじゃなくて、新しい別の関数（オーバーロード）を作りたいんだな」と勘違いしてしまいます。

### 4. 【応用】親の関数を呼び出しつつ、機能を追加したい時は？

オーバーライドすると親の処理は「上書き」されて消えてしまうように見えますが、実は完全に消滅したわけではありません。**「スコープ解決演算子（`::`）」**を使うことで、オーバーライドした関数の中からでも親の元の関数を呼び出すことができます。

実はこれ、`ex03` の `DiamondTrap` の実装（修正版）で使ったテクニックです。

```cpp
// DiamondTrap側で一旦オーバーライドする
void DiamondTrap::attack(const std::string& target) {
    // 自分では処理を書かず、親（ScavTrap）のattackを明示的に呼び出す！
    ScavTrap::attack(target);
}
```

例えばゲームのUIプログラミングなどで、「ボタンが押された時、親クラスの『音を鳴らす』処理はそのまま使いつつ、子クラス独自の『画面を光らせる』処理を追加したい」といった場合に、この `親クラス::関数名()` という呼び出し方が非常によく使われます。

---

**まとめ：**
* **オーバーロード** ＝ 同じ名前で、**引数が違う**バリエーションを増やすこと。
* **オーバーライド** ＝ 親からもらった関数を、**完全に同じ名前と引数**で、自分専用に上書きすること。

## ex03: Now it’s weird! 


この課題（Subjectのタイトル："Now it's weird!" = 「さて、ここからが奇妙だぞ！」）の目的は、ズバリ **「多重継承（Multiple Inheritance）」** と、それに伴って発生する **「菱形継承問題（Diamond Problem）」** というC++特有の厄介な現象を理解し、解決することです。

### 1. 「多重継承」と「菱形（ダイヤモンド）問題」とは？

これまで作ってきた `ScavTrap` と `FragTrap` の**両方の能力を併せ持つ最強（？）のハイブリッドロボット `DiamondTrap`** を作るのが今回の目標です。

クラスの家系図（継承関係）を図にすると、見事な**菱形（ダイヤモンド型）**になります。

```text
         ClapTrap (祖父)
         /      \
        /        \
ScavTrap (父)    FragTrap (母)
        \        /
         \      /
     DiamondTrap (子)
```

**【何が問題なのか？】**
普通に `DiamondTrap` が両親から継承すると、「父（Scav）の中にいる祖父（Clap）」と「母（Frag）の中にいる祖父（Clap）」の**2つの ClapTrap が DiamondTrap の中にダブって生成されてしまう**という大問題が発生します。
「HPを減らせ」と命令したとき、右のClapTrapと左のClapTrap、どちらのHPを減らせばいいかコンパイラが混乱してエラーになります。これを「菱形継承問題」と呼びます。

### 2. DiamondTrap のキメラ的な仕様（Subjectの要求）

Subjectでは、両親から都合よくステータスをつまみ食いする「キメラ」のような設計が要求されています。

* **Hit points (HP):** `FragTrap` の値 (100)
* **Energy points (EP):** `ScavTrap` の値 (50)
* **Attack damage (AD):** `FragTrap` の値 (30)
* **`attack()` 関数:** `ScavTrap` のものをそのまま使う

### 3. 最大の罠：「名前のシャドウイング」

この課題をさらに「奇妙」にしているのが名前（`name`）の扱いです。

1. `DiamondTrap` 自身に、親と同じ `name` という名前のプライベート変数を持たせなさい、と指示されています。
2. これにより、親の `name` が隠れてしまう**「シャドウイング（名前の隠蔽）」**が起きます。
3. `DiamondTrap` 自身の名前（例："Dia"）とは別に、大元の `ClapTrap` の名前には `Dia_clap_name` のように `_clap_name` を付けたものを設定しなければなりません。

そして最後に、`whoAmI()` という特殊能力を追加し、「自分の名前（Dia）」と「ClapTrapとしての名前（Dia_clap_name）」の両方を名乗らせる、という機能を作ります。

---


### 1. 仮想継承（`virtual`）による菱形問題の解決

まずは、なぜ `virtual` というキーワードが必要だったのか、その全体像を見ていきましょう。

#### 【`virtual` がない場合（大惨事）】
もし `ScavTrap` と `FragTrap` の継承時に `virtual` をつけずに `DiamondTrap` を作ると、メモリの中身は以下のようになります。

```text
[DiamondTrap の中身]
 ├── ScavTrap のパーツ
 │    └── ClapTrap (A)  ← Scav用の土台
 └── FragTrap のパーツ
      └── ClapTrap (B)  ← Frag用の土台
```

**起きる問題（コンパイラの混乱）：**
この状態で `diamond.takeDamage(10);` と命令したとします。するとコンパイラは**「えっ？ ダメージを受けるのは ClapTrap(A) と ClapTrap(B) のどっちのHPを減らせばいいの！？」**とパニックになり、コンパイルエラー（曖昧さのエラー）を引き起こします。これが「菱形継承問題」です。

#### 【`virtual` をつけた場合（解決）】
これを解決するために、`ScavTrap` と `FragTrap` の定義で `virtual public ClapTrap` と書きました。
`virtual`（仮想的）と宣言することは、コンパイラに対して**「もし将来、私たちが同じ子孫（DiamondTrap）の中で合流することがあったら、大元の土台（ClapTrap）はダブらせず、1つだけ作ってシェアしようね」**という約束を取り付ける意味があります。

```text
[DiamondTrap の中身]
 ├── ScavTrap のパーツ ──┐
 │                       │ (シェア!)
 ├── FragTrap のパーツ ──┤
 │                       v
 └─────────────────> ClapTrap (共有の土台)
```

#### 💡 仮想継承の「最大の掟」
土台が1つになったことで、もう一つ重要なルールが生まれます。
それは、**「共有の土台（ClapTrap）を初期化する責任と権利は、一番最後に生まれた『最派生クラス（DiamondTrap）』が独占する」**というルールです。

先ほどの実行ログで、`ScavTrap` が自分が渡されたはずの `"Dia"` ではなく `"Dia_clap_name"` を名乗っていたのはこの掟のせいです。
`DiamondTrap` が `ClapTrap` を `"Dia_clap_name"` として初期化してしまったため、途中の `ScavTrap` や `FragTrap` が「俺は "Dia" だ！」と主張しても、コンパイラに**完全に無視（スキップ）**され、すでに完成している共有の土台のデータを読み取ったからです。

### 2. 名前のシャドウイング（Name Shadowing）

次に「シャドウイング（隠蔽）」についてです。
これはプログラミング全般に存在する概念で、**「内側のスコープで、外側と同じ名前の変数を宣言すると、外側の変数が見えなくなる（隠れてしまう）」**という現象を指します。

#### 具体例で見るシャドウイング
一番身近なシャドウイングは、クラスの変数と関数の引数が被った時です。

```cpp
class MyClass {
private:
    int value = 10; // 外側の変数

public:
    void setValue(int value) { // 内側の変数（引数）
        // ここで単に value と書くと、引数の方（内側）が優先される！
        // クラスの value（10）は「シャドウイング」されて隠れてしまう。

        // だから this-> をつけて「外側のクラス変数のことだよ」と明示する
        this->value = value;
    }
};
```

#### DiamondTrap におけるシャドウイング
`ex03` では、これと同じことが「親子クラス間」で起きています。

親クラス（`ClapTrap`）が `name` を持っているのに、子クラス（`DiamondTrap`）でわざわざもう一度 `name` を宣言しました。

```cpp
class ClapTrap {
protected:
    std::string name; // 親のname
};

class DiamondTrap : public ScavTrap, public FragTrap {
private:
    std::string name; // 子のname（← これが親のnameをシャドウイングする！）
};
```

**起きる現象：**
`DiamondTrap` の関数の中で、単に `this->name` と書くと、**自分自身の（子の）`name` が優先され、親の `name` は影に隠れてアクセスできなくなります。**

**隠れた親の変数にアクセスする方法：**
影に隠れた親の `name` を引っ張り出すためには、`whoAmI()` で実装したように、**スコープ解決演算子（`::`）**を使って「どのクラスの変数か」を明示的に指名手配する必要があります。

```cpp
// DiamondTrap の whoAmI 関数の中
std::cout << "私自身の名前は " << this->name << std::endl;
std::cout << "隠れた親の名前は " << ClapTrap::name << std::endl; // :: で指名！
```

#### 💡 なぜわざわざこんなことをするのか？
実際のシステム開発では、シャドウイングは「バグの温床」になるため基本的に**御法度（アンチパターン）**です。（だから `-Wshadow` という警告フラグが存在します）。


---

### 1. `-Wshadow` フラグとは何か？

`gcc` や `clang` などのC++コンパイラに用意されている**警告オプション（フラグ）**の一つです。

コンパイル時に `c++ -Wshadow main.cpp` のように指定すると、コードの中に**「外側のスコープにある変数と同じ名前の変数を、内側のスコープで作ってしまっている場所（＝シャドウイング）」**があった場合、コンパイラが「警告（Warning）」を出して教えてくれます。

### 2. なぜこのフラグが必要なのか？（シャドウイングの怖さ）

シャドウイングは、プログラマーが**「意図せず別の変数を書き換えてしまう（または読み込んでしまう）バグ」**の最大の原因の一つだからです。

以下の恐ろしい例を見てみてください。

```cpp
#include <iostream>

int x = 100; // 外側の変数（グローバル）

void calculate() {
    int x = 10; // 内側の変数（外側のxをシャドウイング！）

    // プログラマーは外側の100に50を足して 150 にしたつもり...
    x = x + 50; 
}

int main() {
    calculate();
    std::cout << x << std::endl; // 結果は 100 のまま！
    return 0;
}
```

このコードでは、`calculate` 関数の中で新しく `int x` を作ってしまったため、外側の `x` が影に隠れてしまいました。結果として、いくら足し算をしても外側の `x` はずっと `100` のままです。

大規模な開発になると、何百行も離れた場所にある変数をうっかりシャドウイングしてしまい、「計算結果が合わない！なぜだ！」と何時間も悩むハメになります。

### 3. `-Wshadow` が教えてくれる 3つの主なシャドウイング

このフラグを有効にすると、以下のようなケースでコンパイラが「警告」を出してくれます。

1.  **ローカル変数が、グローバル変数を隠している時**（上記の例）
2.  **ブロック `{}` の中の変数が、関数の引数や外側の変数を隠している時**
    ```cpp
    void doSomething(int count) {
        if (true) {
            int count = 5; // 警告！引数のcountを隠している！
        }
    }
    ```
3.  **子クラスのメンバ変数が、親クラスのメンバ変数を隠している時** ★（ex03のケース）
    ```cpp
    class ClapTrap { protected: std::string name; };
    class DiamondTrap : public ClapTrap { private: std::string name; }; // 警告！親のnameを隠している！
    ```

### 4. `-Wno-shadow` とは何か？

フラグに `no-` をつけると、**「その警告を無視する（無効化する）」**という意味になります。

つまり、`-Wno-shadow` は**「シャドウイングが起きているのは分かっているから、いちいち警告を出さないでくれ！」**とコンパイラを黙らせるためのフラグです。

### 5. 【結論】Subjectはなぜこのフラグを聞いてきたのか？

42のSubject（ex03）は、わざと `DiamondTrap` に `name` を持たせ、親の `name` をシャドウイングさせるという**「普通なら絶対にやらない悪い設計（Weird!）」**を要求してきました。

そして、Makefile の要件には `-Wall -Wextra -Werror` があります。`-Werror` は「どんな警告もすべてエラーとして扱い、コンパイルを止める」という厳しいフラグです。

もし、評価者が意地悪をして `make CXXFLAGS="-Wall -Wextra -Werror -Wshadow"` と実行してコンパイルした場合、シャドウイングの警告がエラーに変換され、**あなたのプログラムはコンパイルに失敗して0点になってしまいます。**

だからこそ、Subjectは最後にこう問いかけているのです。

> 「君のコードは意図的にシャドウイングを起こしている。もしコンパイラに `-Wshadow` をつけられて怒られた時、それを防ぐための `-Wno-shadow` というお守りの存在を知っているかい？」

これを理解した上で、自衛のために Makefile に `-Wno-shadow` をこっそり仕込んでおく（あるいは、評価者に聞かれた時に「シャドウイングをわざと起こしているから、このフラグをつけると警告が出ますよ」と説明できる）のが、この課題の真のゴール。
