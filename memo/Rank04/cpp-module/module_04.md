# C++ Module 03


## ex00: Polymorphism

語源はギリシャ語の「Poly（多くの）」と「Morph（形）」から来ています。プログラミングにおいては、「同じ指示（関数呼び出し）を出しても、受け取るオブジェクトの種類によって、実際の動作が異なる仕組み」のことを指します。

### 日常生活での例え：リモコンの「電源ボタン」

ポリモーフィズムを直感的に理解するために、家電のリモコンを想像してみてください。

* テレビに向けて「電源ボタン」を押す ➔ **テレビがつく**
* エアコンに向けて「電源ボタン」を押す ➔ **風が出る**
* オーディオに向けて「電源ボタン」を押す ➔ **音楽が鳴る**

私たちは「電源ボタンを押す」という**全く同じアクション（統一されたインターフェース）**をしているだけですが、信号を受け取った家電（オブジェクト）が、自身の性質に合わせて**勝手に適切な動作**をしてくれますよね。これがポリモーフィズムの考え方です。

---

### プログラミングにおけるメリット

先ほどの `Animal` クラスを例に、なぜこの仕組みが嬉しいのかを見てみましょう。

もしポリモーフィズムがなかったら、動物の配列をループ処理で鳴かせたい場合、以下のようなコードを書かなければなりません。

```cpp
// ポリモーフィズムがない場合の最悪なコード例
for (int i = 0; i < animalCount; i++) {
    if (animals[i].type == "Dog") {
        animals[i].bark();
    } else if (animals[i].type == "Cat") {
        animals[i].meow();
    } else if (animals[i].type == "Cow") {
        animals[i].moo(); // 動物が増えるたびにif文を書き足す必要がある...
    }
}

```

しかし、ポリモーフィズム（`virtual makeSound()`）を使えば、次のように書けます。

```cpp
// ポリモーフィズムがある美しいコード
for (int i = 0; i < animalCount; i++) {
    animals[i]->makeSound(); // 全部これだけでOK！
}

```

**最大のメリットは「拡張性（メンテナンスのしやすさ）」です。**
後から `Cow` や `Duck` という新しいクラスを追加しても、呼び出す側のコード（`for`ループの中身）は**一切変更する必要がありません。** ただ新しいクラスを作って `makeSound()` を実装するだけで、システム全体が破綻なく拡張されていきます。

このように「呼び出す側は相手の正体を深く知らなくても、共通のルールで扱える」というのが、ポリモーフィズムがもたらす魔法です。

---

C++におけるポリモーフィズムは、関数が「いつ」決定されるかによって、大きく「コンパイル時」**と**「実行時」の2つのアプローチに分かれます。


### 1. コンパイル時のポリモーフィズム（静的バインディング）

プログラムを実行する前、**ソースコードを翻訳（コンパイル）している段階**で「どの関数を呼ぶか」がカチッと決まるアプローチです。

* **代表例:**
* **関数オーバーロード:** 同じ名前の関数でも、引数の型や数が違えば別の関数として扱われる仕組み。
* **演算子オーバーロード:** `+` や `=` などの記号の働きをクラスごとに定義する仕組み。（Module 02で実装しましたね！）
* **テンプレート:** 型だけを後から決める汎用的な関数やクラスを作る仕組み。（今後のModule 07で学びます）


* **特徴:**
* **速い:** 実行する前にすべての行き先が決まっているため、実行時のオーバーヘッド（遅延）が一切ありません。
* **安全:** 型の間違いなどのエラーを、プログラムを動かす前にコンパイラが発見してくれます。
* **柔軟性に欠ける:** プログラムが走り出してから「やっぱりこっちの型として扱おう」と変更することはできません。



### 2. 実行時のポリモーフィズム（動的バインディング）

プログラムが**実際に動いている最中**に、オブジェクトの「本当の正体」を確認して「どの関数を呼ぶか」を決定するアプローチです。

* **代表例:**
* **仮想関数（`virtual`）とオーバーライド:** 今回のModule 04で実装した `Animal` と `Dog` / `Cat` の関係です。


* **特徴:**
* **極めて柔軟:** コンパイル時には「ただのAnimalのポインタ」としか分からなくても、実行時に「中身はDogだからDogの音を鳴らそう」と動的に対応できます。異なるクラスを同じ配列に突っ込んで一括処理できるのはこのおかげです。
* **少しだけ遅い:** 関数を呼ぶ瞬間に「仮想関数テーブル（vtable）」という内部のリストを毎回見に行ってから実行するため、静的バインディングに比べるとごくわずかに処理コストがかかります。



---

### 💡 2つの違いまとめ

| 比較項目 | コンパイル時（静的） | 実行時（動的） |
| --- | --- | --- |
| **決定タイミング** | コンパイルしている時 | プログラムが動いている時 |
| **主な機能** | オーバーロード、テンプレート | 仮想関数（`virtual`）、オーバーライド |
| **実行速度** | 最速（オーバーヘッドなし） | わずかに遅い（vtableの参照コスト） |
| **柔軟性** | 低い（事前に型が確定している必要あり） | 高い（実行時に型が変わっても対応可能） |
| **42課題での登場** | Module 02 など | Module 04 |


### 1. `virtual` によるポリモーフィズムの実現について

この仕組みを理解するには、コンパイラが関数を呼び出すタイミングである「静的バインディング（コンパイル時）」**と**「動的バインディング（実行時）」の違いを知る必要があります。

**もし `virtual` がなかったら（静的バインディング）**

```cpp
Animal* j = new Dog();
j->makeSound();

```

* コンパイラはコードを翻訳する際、「`j` は `Animal*`（Animal型のポインタ）だな。なら、とりあえず `Animal` クラスの `makeSound()` を呼び出すようにコードを固定（バインド）しておこう」と判断します。
* ポインタの中身が実際に何（DogなのかCatなのか）であるかは**見ません**。箱のラベル（型）だけを見て決定してしまいます。これが `WrongAnimal` で起きていた現象です。

**`virtual` がある場合（動的バインディング）**

```cpp
// Animalクラスでの定義: virtual void makeSound() const;
Animal* j = new Dog();
j->makeSound();

```

* コンパイラは `virtual` というキーワードを見ると、「あ、この関数は派生クラスで上書き（オーバーライド）される可能性があるな。だから今（コンパイル時）はどの関数を呼ぶか固定できないぞ」と考えます。
* 代わりに、実行時にインスタンスの正体を確認して、適切な関数を呼び出す仕組み（仮想関数テーブル：vtable）をこっそり埋め込みます。
* プログラムを実行した際、`j->makeSound()` の地点で「おっと、ラベルは `Animal` だけど、中に入っている本当の姿は `Dog` だな！よし、`Dog::makeSound()` を呼ぼう！」と動的に判断してくれます。これがポリモーフィズムの正体です。

---

### 2. 今回はどうして `new` を使用して動的に確保をしているのか？

主に **「ポリモーフィズムはポインタ（または参照）越しでしか機能しないから」** および **「オブジェクトスライシング（スライス現象）を防ぐため」** です。

もし `new` （やポインタ）を使わずに、直接変数に代入しようとするとどうなるでしょうか？

```cpp
Dog myDog;
Animal myAnimal = myDog; // 値渡し（ポインタではない）
myAnimal.makeSound();    // Animalの音が鳴ってしまう！

```

これを**オブジェクトスライシング**と呼びます。`Dog` にしかないデータや特徴が、`Animal` 型の変数に無理やり詰め込まれる際に「削ぎ落とされて（スライスされて）」しまい、完全にただの `Animal` に成り下がってしまいます。

ポリモーフィズムの「基底クラスのフリをして、実は派生クラスとして振る舞う」という性質を利用するには、実体そのものを削ぎ落とすのではなく、「基底クラスのポインタ（`Animal*`）で、ヒープ領域などに存在する派生クラスの実体（`new Dog()`）を指し示す」必要があります。
そのため、今回のSubjectでは `new` を使って動的にメモリを確保し、ポインタを通じて操作する設計になっています。

---

### 3. ポインタを介さず直接呼べば `Wrong Meow!` と鳴るのはどうしてか？

これは非常に鋭い着眼点です！
`virtual` がついていない `WrongCat` であっても、以下のように直接呼び出した場合は正しく `WrongCat` の音が鳴ります。

```cpp
WrongCat wcat1;
wcat1.makeSound(); // "Wrong Meow!" と鳴る

```

**なぜか？**
それは、**コンパイラにとって「迷い」が一切ないから**です。

先ほどのポインタの例（`WrongAnimal* wrongI = new WrongCat();`）では、**「箱のラベルは WrongAnimal だが、中身は WrongCat」** という矛盾（ポインタのアップキャスト）があったため、コンパイラは箱のラベルだけを信じて `WrongAnimal` の関数を呼んでしまいました。

しかし、`WrongCat wcat1;` の場合は、箱のラベルも中身も 100% `WrongCat` です。
コンパイラは「これは間違いなく `WrongCat` だ。ポインタの型変換も起きていない。だからそのまま `WrongCat::makeSound()` をコンパイル時に固定（静的バインディング）してしまおう」と判断します。

つまり、`virtual` （実行時の型チェック）が必要になるのは、**「親クラスのポインタ（または参照）を使って、子クラスを操作しようとした時だけ」** なのです。直接自分の型として扱う分には、`virtual` は全く関係なく、自分の関数がそのまま呼ばれます。

## ex01: I don’t want to set the world on fire

---

### 1. シャローコピーとディープコピーの違い

**❌ シャローコピー（浅いコピー）の場合**
C++がデフォルトで行うコピーは、単なる変数の丸写しです。
もし `Dog B = Dog A;` とした場合、Aが持っている `brain` の「メモリアドレス」だけがBにコピーされます。
結果として、**AとBが全く同じ脳（1つのBrainインスタンス）を共有してしまう**ことになります。

* **悲劇1**: Bが「おやつが欲しい」と脳に書き込むと、Aの脳まで「おやつが欲しい」に上書きされてしまいます（自我の喪失）。
* **悲劇2（致命的）**: Bの寿命が尽きてデストラクタが呼ばれると、共有していた `Brain` が `delete` されます。その後、Aが死ぬ時にもう一度同じ `Brain` を `delete` しようとしてしまい、**「Double Free（二重解放）」という致命的なエラーでプログラムがクラッシュ**します。

**⭕ ディープコピー（深いコピー）の場合**
これを防ぐため、コピー時には「新しくメモリを確保（new）して、中身のデータだけをそっくり書き写す」という処理を自前で書く必要があります。これがディープコピーです。

---

#### ① RAIIの原則（コンストラクタとデストラクタ）

前回のフィードバックにもあった「RAII（Resource Acquisition Is Initialization）」の概念がここで活きます。

*
**コンストラクタ**: `Dog` が生まれた瞬間に `this->brain = new Brain();` で脳のメモリを確保します 。


*
**デストラクタ**: `Dog` が死ぬ瞬間に `delete this->brain;` で必ず脳のメモリを解放します 。
これにより、「Dogが存在する限り、必ず自身のBrainが存在し、Dogが消えればBrainも消える」という安全な状態を作ります。



#### ② コピーコンストラクタの実装

新しく `Dog` を別の `Dog` から作る際の処理です。

```cpp
Dog::Dog(const Dog& other) : Animal(other) {
    // otherの脳のアドレスをコピーするのではなく、otherの脳を元に新しく脳を作り出す
    this->brain = new Brain(*other.brain);
}

```

#### ③ 代入演算子（`operator=`）の実装

すでに存在している `Dog` に対して、別の `Dog` のデータを上書きする際の処理です。ここが一番間違いやすいポイントです。

```cpp
Dog& Dog::operator=(const Dog& other) {
    if (this != &other) { // 自分自身への代入を防ぐ
        this->type = other.type;

        // 🚨重要: 自分が元々持っていた古い脳を捨てないと、メモリリークになる！
        delete this->brain;

        // その上で、新しく相手の脳のコピーを作る
        this->brain = new Brain(*other.brain);
    }
    return *this;
}

```

#### ④ ポリモーフィズムと仮想デストラクタの真価

main関数では、「`Animal*` の配列に `Dog` と `Cat` を半分ずつ詰め込み、ループで全て `delete` する」というテストを行いました 。
もし `Animal` クラスのデストラクタに `virtual` を付け忘れていると、`delete animals[i]` とした時に `Animal` のデストラクタしか呼ばれず、`Dog` や `Cat` のデストラクタが無視されてしまいます。
その結果、**彼らの `Brain` が解放されずに大量のメモリリークが発生**します。ex00で `virtual ~Animal()` とした恩恵が、ここでようやく目に見える形で現れるという見事な課題構成になっています 。

---

まとめると、ex01は「ポインタをメンバに持つクラスは、必ず自分でディープコピー（コピーコンストラクタと代入演算子）と適切なデストラクタを書かなければならない」という、C++プログラマの鉄則（Rule of Three）を叩き込むための課題です。

---

### 1. コンストラクタの順番（家を建てる順番）

C++でオブジェクトが作られる時、**「基礎（親クラス） → 内装（メンバ変数） → 外観（子クラス自身）」** の順番で構築されます。

`new Dog()` を実行した時の裏側の動きを見てみましょう。

1. **`Animal default constructor called`**
* `Dog` は `Animal` を継承しています。犬（子）として生まれる前に、まず動物（親）としての基礎を完成させる必要があります。そのため、一番最初に `Animal` のコンストラクタが自動的に呼ばれます。


2. **`Brain default constructor called`**
* 基礎ができたら、次は `Dog` の中身（メンバ）を作ります。`Dog` のコンストラクタの中で `this->brain = new Brain();` と書きましたよね。ここで脳みそが生成されます。


3. **`Dog default constructor called`**
* 親クラスの準備ができ、脳みその準備もできたので、最後に `Dog` 自身のコンストラクタの処理（`std::cout` の出力など）が完了します。



（※ `Cat` の生成時も全く同じ順番で呼ばれています）

---

### 2. デストラクタの順番（家を解体する順番）

オブジェクトが破棄される時は、「生成した時と完全に逆の順番（巻き戻し）」で行われます。内装を片付けてから、最後に基礎を壊すイメージです。

`delete j;` （`j` は `Dog` を指す `Animal*`）を実行した時の動きです。

1. **`Brain destructor called`**
* まず `Dog` のデストラクタに入ります。コード内で一番最初に `delete this->brain;` と書いたため、まず脳みそ（メンバ）が解体されます。


2. **`Dog destructor called`**
* 脳みその解放が終わると、`Dog` 自身のデストラクタの処理（`std::cout` の出力）が完了し、犬としての姿が消えます。


3. **`Animal destructor called`**
* 子クラス（`Dog`）の解体がすべて終わると、コンパイラは自動的に親クラス（`Animal`）のデストラクタを呼び出し、動物としての基礎部分を綺麗に解体します。



---

### 💡 この出力が「大成功」である最大の理由

もし、基底クラスである `Animal` のデストラクタに **`virtual` を付け忘れていた場合**、出力は以下のようになってしまいます。

```text
// 失敗例（virtualがない場合）
Animal destructor called
Animal destructor called

```

ポインタの型が `Animal*` だからといって、コンパイラが `Dog` や `Brain` の存在を無視して、表面上の `Animal` 部分だけを壊して終わってしまうのです。これが**メモリリークの最大の原因**です。


## ex02: Abstract class

この課題は、オブジェクト指向プログラミングにおける非常に重要な概念である「抽象クラス」**と**「純粋仮想関数」について学ぶためのものです。

### 1. 課題の概要（なぜ抽象クラスが必要なのか？）

現実世界を想像してみてください。「犬」や「猫」という具体的な生き物は存在しますが、**ただの「動物」というフワッとした実体は存在しませんよね。**
「動物の鳴き声を出して」と言われても、「いや、犬なのか猫なのか指定してくれないと鳴けないよ！」となるはずです。

Exercise 01までの `Animal` クラスは、`new Animal()` として実体化（インスタンス化）できてしまう状態でした。
Subject（課題文）では、「そもそも『動物』という実体を生成できるのはおかしい。間違えてただの動物を作れないように修正しなさい」と指示されています。

この「概念（ベース）としては必要だけど、実体化されては困るクラス」を作る仕組みが、**抽象クラス（Abstract class）** です。

---

### 2. コードの内容と実装のポイント

この課題をクリアするために、ex01のコードにわずかな、しかし非常に強力な変更を加えました。

#### ① クラス名の変更（`Animal` ➔ `AAnimal`）

Subjectの「抽象クラスであることが分かりやすいように、名前に `A` をつけてもよい」という提案に従い、クラス名を `AAnimal` に変更しました。（AはAbstractの頭文字です）。

#### ② 「純粋仮想関数」の導入（ここが核心！）

クラスを「抽象クラス」にするためには、C++では「純粋仮想関数（Pure Virtual Function）」を最低1つ持たせる必要があります。

**AAnimal.hpp** のコードを見てみましょう。

```cpp
class AAnimal {
    // ...
    // 普通の仮想関数（ex00, ex01）
    // virtual void makeSound() const;

    // 純粋仮想関数（ex02）
    virtual void makeSound() const = 0;
};

```

末尾に **`= 0;`** をつけるだけです。
この `= 0;` は、コンパイラに対して以下の2つの強いメッセージ（ルール）を伝えます。

1. **「このクラス (`AAnimal`) は未完成なので、絶対に `new` で実体化させないでくれ！」**
2. **「このクラスを継承する子クラス (`Dog` や `Cat`) は、絶対に自分自身で `makeSound()` の中身を作れ（オーバーライドしろ）！」**

#### ③ Dog クラスと Cat クラス（具象クラス）

`Dog` や `Cat` クラスの実装は ex01 とほぼ同じ（親が `AAnimal` に変わっただけ）です。
彼らは `AAnimal` から引き継いだ「絶対に `makeSound()` を作れ」というルールを守り、ちゃんと `Woof!` や `Meow!` と鳴くように上書き（オーバーライド）しています。
このように、すべての純粋仮想関数を実装し終えて実体化できるようになったクラスを具象クラス（Concrete class）と呼びます。

#### ④ main.cpp でのテスト

この課題が成功しているかどうかは、以下のコードが**コンパイルエラーになるかどうか**で確認できます。

```cpp
int main() {
    // ❌ これはコンパイルエラーになる！（成功の証拠）
    // AAnimal* errorAnimal = new AAnimal();

    // ⭕ ポインタの「型」として使う分には問題ない（ポリモーフィズム）
    const AAnimal* dog = new Dog();

    dog->makeSound(); // Woof! と鳴く
    delete dog;
}

```

「ただの動物」は作れなくなりましたが、依然として `AAnimal*` という「動物を指差すためのポインタ」としては機能します。
これにより、**「実体化のミスはコンパイル時に防ぎつつ、ポリモーフィズムの便利さはそのまま活かす」** という、非常に安全で美しい設計が完成しました。


「実体化できなくなることの何が嬉しいのか？」
一言で言えば、最大のメリットは「プログラマのミス（論理的なバグ）を、プログラムを実行する前の『コンパイル時』に完全に防ぐことができるから」です。

具体的に、以下の3つの強力なメリットがあります。

### 1. 「あり得ないバグ」を未然に防ぐ（安全性の向上）

現実世界において、「犬」や「猫」は存在しますが、具体的な姿形を持たない「ただの動物」という実体は存在しません。
もし `Animal` クラスが実体化できてしまうと、誰かが間違えて `Animal* a = new Animal();` と書いてしまった場合、プログラム上には「鳴き声も特徴もない、謎の生命体（ただの動物）」が誕生してしまいます。
これを抽象クラスにして実体化を禁止することで、**「『ただの動物』を作ろうとするのは論理的におかしいよ！」とコンパイラがエラーを出して教えてくれる**ようになります。実行してからバグに気づくのではなく、実行する前にミスを潰せるのが最大の強みです。

### 2. 派生クラスへの「ルールの強制」（実装漏れの防止）

純粋仮想関数（`virtual void makeSound() const = 0;`）を持つクラスを継承した場合、子クラスは**絶対にその関数を上書き（オーバーライド）しなければ、自分自身も実体化できない**という厳しいルールが課せられます。
たとえば、新しく `Cow`（牛）クラスを作った開発者が、うっかり `makeSound()` を書き忘れたとします。もしこれが普通の仮想関数なら、牛は「Animalの汎用的な鳴き声」を発するバグを持ったままプログラムが動いてしまいます。
しかし純粋仮想関数であれば、「CowクラスはmakeSound()を実装していないからエラー！」とコンパイル時に弾かれるため、**「新しい動物を追加するなら、必ず鳴き声を定義しろ」というルールを強制**できるのです。

### 3. 他の開発者への「意図の伝達」（設計図としての役割）

実際の開発現場では、複数人でコードを書きます。クラスに `= 0;` がついている（抽象クラスである）のを見た瞬間、他のプログラマは以下のことを一瞬で理解します。

* 「あ、このクラスは直接 `new` して使うものじゃないんだな」
* 「このクラスは、他のクラスを作るための『土台（テンプレート）』として用意されているんだな」

つまり、コードそのものが「このクラスはどう使われるべきか」というマニュアル（ドキュメント）の役割を果たすようになります。

## ex03: Interface & recap

---

### 1. 課題の概要と「インターフェース」とは？

C++98（およびそれ以降のC++）には、JavaやC#のように `interface` という専用のキーワードが存在しません。
しかし、前回の ex02 で学んだ「抽象クラス」を極限まで尖らせて、「メンバ変数を一切持たず、純粋仮想関数（`= 0`）と仮想デストラクタだけを持つクラス」を作ることで、それを「インターフェース」として扱うのがC++の文化です。

インターフェースの役割は「振る舞いのルール（契約）だけを決めること」です。
「中身はどうでもいいから、とにかく『装備する』『使う』という機能を持たせなさい」というルールだけを定義し、実際の中身（実装）はすべて継承先のクラスに任せます。

---

### 2. 登場するクラスの役割（RPGのシステム）

この課題では、大きく3つのグループ（計7つのクラス）を作成しました。

#### ① 魔法（Materia）グループ

* **`AMateria` (抽象クラス)**: すべての魔法のベースとなるクラス。
* **`Ice` / `Cure` (具象クラス)**: 実際の魔法です。それぞれ「氷の矢を放つ」「傷を癒やす」という固有の `use()`（使う）の処理を持っています。

#### ② キャラクター（Character）グループ

* **`ICharacter` (インターフェース)**: 「名前を持つ」「魔法を装備できる(equip)」「外せる(unequip)」「使える(use)」というルール（契約）の定義。
* **`Character` (具象クラス)**: 実際に魔法を4つまで持てる「インベントリ（配列）」を持ったキャラクターです。

#### ③ 魔法の生成工場（MateriaSource）グループ

* **`IMateriaSource` (インターフェース)**: 「魔法を学習する(learn)」「魔法を生み出す(create)」というルールの定義。
* **`MateriaSource` (具象クラス)**: 魔法の雛形（テンプレート）を最大4つまで記憶できる「魔法の書」のような存在です。

---

### 3. コードの核心・実装のハイライト

#### 💡 ハイライト1: 魔法のクローン生成（Prototypeパターン）

一番の魔法の仕掛けが、`AMateria` にある **`clone()`** 関数です。
`MateriaSource` は、"ice" という文字列を受け取ると、記憶している `Ice` のテンプレートに「自分自身のコピーを作って！」と指示を出します（`templates[i]->clone()`）。
これにより、「相手の本当の型（IceかCureか）を知らなくても、とりあえず `clone()` を呼べば正しい魔法が生成される」という、極めて柔軟で美しい設計（Prototypeパターン）が実現されています。

#### 💡 ハイライト2: Characterのディープコピー（鬼のメモリ管理）

ex01での `Brain` のディープコピーの進化版です。
`Character` は、最大4つの `AMateria*`（魔法へのポインタ）を持っています。
キャラクターをコピーする際、単にポインタのアドレスをコピーする（シャローコピー）と、後で二重解放（Double Free）が起きてしまいます。
そのため、コピーコンストラクタと代入演算子の中で、「相手のインベントリを見て、中身が入っていればその魔法の `clone()` を呼んで新しく自分のインベントリに入れる」という処理（ディープコピー）をループで回して実装しています。

#### 💡 ハイライト3: `unequip`（装備解除）の罠とメモリリーク防止

Subjectには「unequip() はマテリアを delete してはいけない」**と明確に書かれています。
これはRPGで言うところの**「装備を外して、アイテムを床に落とした状態」です。

```cpp
void Character::unequip(int idx) {
    inventory[idx] = NULL; // インベントリから外すだけ（deleteしない）
}

```

しかし、C++では「誰のポインタからも指し示されなくなったメモリ（床に落ちたアイテム）」は永久に回収されないゴミ（メモリリーク）になります。
これを防ぐために、`main.cpp` のテストコードでは、以下のように「床に落ちる前にアドレスを覚えておき、後で自分で拾って捨てる（`delete`する）」という処理を書いていました。

```cpp
// 装備を外すテスト（main.cpp）
AMateria* droppedMateria = src->createMateria("ice");
me->equip(droppedMateria);

me->unequip(2);         // 床に落とす（Characterの手元から離れる）
delete droppedMateria;  // メモリリークを防ぐため、覚えておいたポインタを使って手動で破壊！

```

### 1. なぜ前方宣言が必要になったのか？（循環参照の罠）

Exercise 03 の `AMateria` と `ICharacter` の関係を思い出してください。

* **`AMateria`** は、対象に魔法を使うために `ICharacter` の存在を知る必要があります。
* `virtual void use(ICharacter& target);`


* **`ICharacter`** は、魔法を装備するために `AMateria` の存在を知る必要があります。
* `virtual void equip(AMateria* m);`



もしこれを、お互いに `#include` を使って解決しようとするとどうなるでしょうか？

1. `AMateria.hpp` が `ICharacter.hpp` を読み込みに行く。
2. `ICharacter.hpp` の中を見ると、一番上で `AMateria.hpp` を読み込もうとしている。
3. `AMateria.hpp` の中を見ると、一番上で `ICharacter.hpp` を読み込もうとしている。
4. …（以下無限ループ）

このように、お互いがお互いを `#include` しようとして無限ループに陥る状態を循環参照（Circular Dependency）と呼びます。コンパイラは混乱し、「型が見つからない」といった大量のエラーを吐き出して止まってしまいます。

### 2. 前方宣言による解決

この「無限ループ」を断ち切る魔法の言葉が、前方宣言です。

`ICharacter.hpp` の中では `#include "AMateria.hpp"` を書く代わりに、**`class AMateria;`** とだけ書きます。

```cpp
#ifndef ICHARACTER_HPP
#define ICHARACTER_HPP

#include <string>

// 「AMateriaっていうクラスがどこかにあるよ！」という予告（前方宣言）
class AMateria; 

class ICharacter {
public:
    virtual ~ICharacter() {}
    virtual void equip(AMateria* m); // コンパイラ「なるほど、AMateriaのポインタね。OK！」
};

#endif

```

これにより、コンパイラは「中身はよく分からないけど、`AMateria` っていう名前のクラスが存在することだけは分かった。ならポインタを受け取る関数は作れるな！」と納得してくれ、無限ループを回避してコンパイルを進めてくれます。

---

### 3. 前方宣言の「絶対的なルール」

前方宣言には、一つだけ**超重要で厳格なルール**があります。

それは、「前方宣言しただけのクラスは、ポインタ（`*`）か参照（`&`）としてしか使えない」というルールです。

**⭕ 許される使い方（ポインタ・参照）**

```cpp
class AMateria;

AMateria* pointerMateria; // OK! ポインタのサイズは常に一定だから。
AMateria& refMateria;     // OK! 参照もアドレスを扱うだけだから。

```

**❌ 許されない使い方（実体化・値渡し）**

```cpp
class AMateria;

AMateria normalMateria;     // コンパイルエラー！中身のサイズが分からない！
void doSomething(AMateria m); // コンパイルエラー！コピーするサイズが分からない！

```

#### なぜ実体（値）としては使えないのか？

コンパイラがメモリを確保する際、「そのクラスが何バイトのメモリを必要とするか（サイズ）」を知らなければなりません。
`#include` をすればクラスの完全な設計図が読めるのでサイズが分かりますが、前方宣言は「名前」を教えただけなので、コンパイラは「どんな変数を持っていて、何バイト必要なクラスなのか全く分からないよ！」とお手上げになってしまうのです。

一方、ポインタ（アドレスを指す矢印）や参照のサイズは、中身がどんな巨大なクラスであろうと、常に一定（64ビットOSなら8バイト）です。
そのため、コンパイラは中身のサイズを知らなくても、「とりあえず8バイトのポインタ箱を用意しておけばいいんだな」と処理を進めることができるという仕組みです。

---

### まとめ

* **前方宣言（`class ClassName;`）** は、ヘッダファイル同士の `#include` の無限ループ（循環参照）を防ぐためのテクニック。
* コンパイラに「名前だけ」を教えることで、コンパイルを通すことができる。
* ただし、完全な情報がないため、**ポインタか参照としてしか扱えない**。
* 実際にそのクラスの中身の関数（`m->use()` など）を呼び出す時（`.cpp` ファイルの中）には、完全な設計図が必要なので `#include "AMateria.hpp"` を書く必要がある。
