# 技術スタック比較: TypeScript統一 vs Elixir/Phoenix

> MTG #1 議題3（技術スタック）の判断材料。
> 前提要件は [requirements.md](requirements.md) §3、モジュール構成は [module-plan.md](module-plan.md) を参照。
> フロントは両案とも React + Vite + Tailwind で共通。**比較対象はバックエンドのみ**。

---

## 0. 両案とも満たせること（差がつかない点）

- FWフロント+バック Major(2pt) — NestJS / Phoenix いずれも Subject のフレームワーク定義を満たす
- WebSocketリアルタイム Major(2pt)
- ORM Minor(1pt) — Prisma / Ecto
- Docker Compose 1コマンド起動、HTTPS、メール+パスワード認証

→ **モジュールポイント上はどちらを選んでも同じ。** 差が出るのは開発体験とリスク。

---

## 1. 比較表

| 観点 | TypeScript (NestJS + Socket.IO) | Elixir (Phoenix) | 優位 |
|---|---|---|---|
| 学習コスト | JS経験があれば低い。NestJSの構造だけ覚える | 関数型+動的型付け。C/JS の感覚から転換が必要（目安1ヶ月） | **TS** |
| 情報量・詰まった時の脱出速度 | 日本語含め最大級 | 一桁少ない。英語ドキュメント前提 | **TS** |
| フロントとの型共有 | ◎ ゲームイベントの型を共有パッケージ化できる | ✕ 言語が分かれる。イベント定義の二重管理が必要 | **TS** |
| リアルタイム機能の実装量 | Socket.IO で再接続・ルームは標準。ブロードキャスト設計は自前 | Channels + **Presence**（オンライン状態追跡）+ PubSub が標準装備 | **Elixir** |
| ゲーム状態の並行管理 | 1プロセス内で全ルームを管理。排他制御は自前で規律 | 1ルーム=1プロセスで状態が隔離。レースコンディションが構造的に起きにくい | **Elixir** |
| 耐障害性 | プロセスが落ちると全ルーム道連れ（PM2等で緩和） | Supervisor がルーム単位で自動復旧 | **Elixir** |
| 4人での分業しやすさ | NestJS のモジュール分割が担当分けに直結。全員が front/back 両方触れる | バックエンド担当が実質固定化しやすい | **TS** |
| 評価時の説明リスク | 低い。枯れた定番構成 | 「なぜElixir?」への回答は必要（≒READMEの正当化ネタになる面も） | **TS** |
| 採用実績（説得材料） | ほぼ全て | WhatsApp(Erlang), Discord — チャットゲームの先行事例として強い | — |

## 2. 各案の具体構成

### 案A: TypeScript統一（本命）

| レイヤ | 技術 |
|---|---|
| バック | NestJS + Socket.IO |
| DB | PostgreSQL + Prisma |
| 共有 | `packages/shared` にイベント型・バリデーションスキーマ(zod)を配置 |

### 案B: Elixir挑戦（条件付き）

| レイヤ | 技術 |
|---|---|
| バック | Phoenix (Channels / Presence / PubSub) |
| DB | PostgreSQL + Ecto |
| 共有 | イベント定義は仕様書で管理（型共有なし） |

## 3. 判断基準（ミーティングで確認すること)

1. **全員のスキル聞き取り** — JS/TS経験者が3人以上 → 案A。関数型経験者（OCamlピシン通過など）が2人以上いて意欲もある → 案Bを検討する資格あり
2. **キャッチアップ期間を1ヶ月取れるか** — 取れないなら案B は選ばない
3. **評価の全員説明責任** — 「一番書けない人」がそのスタックで自分の担当を説明できるか

## 4. 推奨

- **デフォルトは案A（TS統一）。** 完成確実性・分業・型共有で総合的に上。
- 案Bは「リアルタイムゲームとしての技術的完成度」と「企画の面白さ」では上回りうるが、失敗モード（キャッチアップ遅延→ゲーム本体の遅れ→モジュール0pt連鎖）が重い。選ぶなら §3 の条件を全て満たす場合のみ。
