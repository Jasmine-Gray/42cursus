# MTG #1 アジェンダ（キックオフ / 要件定義）

> 目的: 全員が「何を作るか・何が決まっていて・何を決めるべきか」を同じ解像度で持つこと。
> 事前資料: [decisions.md](../requirements/decisions.md), 
[module-plan.md](../requirements/module-plan.md)

---

## 0. 確定事項の共有（10分・議論しない）

- decisions.md を上から流す
  - Subjectの必須要件（却下条件: プライバシーポリシー/利用規約、コンソールエラー、コンテナ1コマンド起動）
  - 14ptモジュール制と「動かないモジュール=0pt」
  - 人狼を作る以上ベース14ptはほぼ自動で決まっていること
- ここは「質問は受けるが議論はしない」で通す

## 1. ゲームの骨格を決める（30分・本題）

| 論点 | 選択肢の例 | 決めること |
|---|---|---|
| 部屋人数 | 最小5人 / 最小4人+AI補充 | 最小成立人数と上限 |
| 進行方式 | 制限時間つきフェーズ制（昼議論→投票→夜行動） | フェーズ制でよいか、1フェーズの時間感 |
| MVP役職 | 犯人・探偵・市民の3種スタート | 最初のバージョンの役職数 |
| 切断処理 | 再接続待ち→AI代打 / 再接続待ち→ゲーム続行(欠員) | 方針だけ（実装詳細は不要） |

## 2. モジュールプランを選ぶ（15分）

- module-plan.md のプランA（堅実16pt）/ B（AI推し17pt+）/ C（分業重視17pt）から方向性を選ぶ
- **AI対戦Majorの採否だけはここで決める**（コア設計に影響するため先送り不可）
- 個別モジュールの細部は決めない

## 3. 技術スタック（15分・TechLead提案の承認）

### 提案: TypeScript統一スタック

| レイヤ | 提案 | 理由 |
|---|---|---|
| フロント | React + Vite + Tailwind CSS | FW Major要件充足。情報量が多く詰まりにくい |
| バック | NestJS（or Fastify） + Socket.IO | FW Major要件充足。WebSocketエコシステムが最も厚い |
| DB | PostgreSQL + Prisma (ORM) | スキーマ明確化の要件 + ORM Minor(1pt)がタダで付く |
| インフラ | Docker Compose + nginx（TLS終端） | 1コマンド起動 + HTTPS要件 |

- 統一の狙い: フロント/バックで言語を分けない → 全員がどこでも手伝える、型をフロント・バックで共有できる
- 対抗案: バックエンドPython（Django Channels / FastAPI）。Python経験者が多いなら検討余地あり。ただし言語が2つになり、リアルタイム系の情報量はNode側が優位
- 対抗案: バックエンドElixir（Phoenix）。詳細比較は [tech-stack-comparison.md](../requirements/tech-stack-comparison.md) を参照


## 4. 運用ルール（10分）

- タスク管理: Notion + (GitHub Issues) 
- 連絡: Discord（提案）
- ミーティング: 週1定例 + 必要時（提案）
- ブランチ運用: main保護 + develop branch + PRレビュー1人以上
- ※評価で「どう組織したか」を聞かれるため、決めた内容はREADME素材として記録する

## 5. 宿題（5分）

- **次回までに人狼系オンラインゲームを1戦遊んでくる**（人狼オンライン、Among Us等）
- 見てくるポイント: フェーズ進行のUI / 切断した人の扱い / 死亡後・観戦者の画面 / チャットの仕様
- 目的: 次回の要件詰めで全員が同じ語彙で話せるようにする

## 決めないこと（宣言してスコープから外す)

- 独自メカニクス（証拠・捜査要素）の詳細
- UIデザイン
- 個別モジュールの実装方法
