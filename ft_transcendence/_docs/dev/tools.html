01選定の原則

  1. 生成するのは型まで。実行時コードは生成しない。 42の評価では自分が説明できないコードは失格になり得るため、生成物は型に限る。 APIの呼び出し方、キャッシュ、hooks、状態管理は手で書く。
  2. 1つの仕事に1つのツール。 多機能な統合ジェネレータより、入力と出力が1対1で追える小さいツールを選ぶ。 壊れたときに原因が即座に分かる。
  3. 開始時点の最新に揃え、期間中は追随しない。 W1で全バージョンを固定し、lockfile と mix.lock をコミットする。 上げるなら専用PRを立て、make gen の差分をレビューする。

CIの実行順

1. 整形の確認     prettier --check / mix format --check-formatted
2. lint          oxlint / mix credo
3. 型            tsc --noEmit / mix dialyzer（PLTキャッシュ）
4. テスト        vitest run --coverage / mix test --cover
5. 契約          make spec-lint / make gen && git diff --exit-code / prism proxy
6. セキュリティ   mix sobelow --exit / mix deps.audit

前段が落ちたら後段は走らせない。整形とlintはlefthookのpre-commitでも回すので、 CIで落ちるのは基本的にフック未導入のときだけになる。

Makefileに集約する

# 実物はリポジトリ直下の Makefile（make help で一覧）
gen: gen-frontend gen-backend

gen-frontend:
	npx --yes openapi-typescript@7.13.0 _docs/spec/api/openapi.yaml \
	  -o frontend/src/types/api.d.ts
	python3 _tools/gen-contract-types.py --only frontend

gen-backend:
	python3 _tools/gen-contract-types.py --only backend

gen-check: gen
	# 生成物の手編集・未コミットを落とす（git status で判定）

spec-lint:
	npx @redocly/cli lint _docs/spec/api/openapi.yaml
	npx @asyncapi/cli validate _docs/spec/api/asyncapi.yaml

lint:
	cd frontend && npx prettier --check . && npx oxlint && npx tsc --noEmit
	cd backend  && mix format --check-formatted && mix credo

audit:
	cd backend && mix sobelow --exit && mix deps.audit

06採用しないツール

ツール理由
openapi-zod-client
1.18.3		 依存が zod: ^3.19.1 で、現行zodは4.4.3。さらに @zodios/core・axios・prettier 2 を引き込む。 「最新で揃える」方針と衝突するうえ、使わないクライアント実装まで生成される。 フォーム検証は契約のJSON Schemaをajvで直接使う（§02）
@hey-api/openapi-ts
orval / kubb		 SDK・Zod・TanStack Query hooksまで1つの設定で生成でき機能的には上位。 ただし実行時コードの生成量が多く「説明できるコード」の原則と衝突する。 0.x系で設定が変わりやすく、Node 22+が前提。 hooksの手書きが辛くなった時点で乗り換え候補にする
eslint + typescript-eslint
10.8.1 / 8.67.0		 oxlintで足りる。設定が二重になり、速度差も大きい。 oxlintで拾えないルールが実際に問題化したときだけ再検討する
@biomejs/biome
2.5.9		 lintと整形が1つになり魅力的だが、mockにoxlint設定が既にあるため乗り換えコストが無駄。 Tailwindクラスのソートも prettier plugin の方が確実。移行するなら4週の期間外
styler
1.12.2		 Elixirコードを自動で書き換えるため、初期導入すると差分が巨大化してレビュー不能になる。 入れるなら実装が固まった後
ex_json_schema / json_xema draft 4（前者）と draft 4/6/7（後者）まで。契約はOpenAPI 3.1.1 = JSON Schema 2020-12 なので合わない
phoenix_swagger
open_api_spex のコード先行スタイル		 Elixirコードで仕様を定義してYAMLを吐く向き。契約の正本がコード側へ移り、 「契約が唯一の正」が崩れる
oapi_generator OpenAPIからクライアントを生成するツール。サーバー側の用途と違う
@asyncapi/modelina
5.10.1		 AsyncAPI 3.1.0 に未対応（3.0.0 まで）。3.0.0 に落として試しても、 messageのpayloadがインライン定義のため AnonymousSchema_16 のような名前で出力され使えない。 契約をツールに合わせて曲げるより自前生成が安い（_tools/gen-contract-types.py、約380行）
AsyncAPI Generator のテンプレート群 Phoenix Channels向けテンプレートが無い。payload型・イベント名・対応表は自前生成で足りる

08導入前に決めること

未決 — ツール導入より先

1. 認証方式。openapi.yaml は bearerAuth（セッショントークン）だが、 architecture/tech-stack.md §4 は「HttpOnly Cookie / トークンをLocalStorageに置かない」。 openapi-fetch のラッパがトークンを保持するかが変わる。

2. ゲーム中操作の経路。tech-stack.md §3 は「原則Channel」だが、 契約と backend-spec.md では start / vote は HTTP POST（配信のみChannel）。契約が正なので §3 を修正する。

要確認 — モックの実依存と tech-stack.md の乖離

_docs/mock/package.json の実際の構成が tech-stack.md の記載と一致していない。 frontend/ へ移植する前にどちらを正にするか決める。

  • ルーティング: mockは wouter 3.10.0 / 文書は React Router（最新8.3.0） — 動いている wouter を採用して文書を直すのが移植コストゼロ
  • UI基盤: mockは @base-ui/react + shadcn CLI / 文書に記載なし
  • REST状態管理: mockは未使用 / 文書は TanStack Query — 使うなら @tanstack/react-query 5.101.4 を追加する（REST画面レーンの判断）
  • TypeScript: mockは ~6.0.2 固定 / 最新は 7.0.2 — W1で通過確認してから上げる
