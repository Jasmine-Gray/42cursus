01概念 — 画面 = f(データ)

「データがある前提」= 画面を、契約で形が決まったデータを表示へ変換する関数として作ること。

02なぜ — 待ちが消える

実物を待つと直列。形（契約）だけ先に固定すれば、FEは「データがある前提」でBEと同時に走れる。

03データの実物は3段階で差し替わる

出どころが 1→2→3 と差し替わっても境界の「形」は同じなので、画面のコードは変わらない。 変わってしまうなら分離に失敗している（設計の警報）。_docs/mock/ の25画面は段階1の実証。

04画面側のルール — 差し替えを1か所に閉じ込める

画面から遠い層ほど差し替わる。出どころの差し替えを最下層に閉じ込めるのが全ルールの目的。 モックデータに生成型を注釈しておくと、契約変更のズレが型エラーで自動検出される。

05落とし穴 — 「データがある」は4状態の1つ

モックデータは success しか見せない。着手時に4状態を列挙し、fixtures に empty / error 用も置いて 段階1のうちに4状態すべてを描画しておく。実結合時の「一瞬 undefined でクラッシュ」「0件でレイアウト崩壊」はここで防ぐ。

06画面01〜04への適用

各画面が「ある前提」にするデータと契約上の出どころ。01・02のフォーム画面では前提が逆向きに働く — 受け取る形ではなく送る形が契約で固定されている前提で入力検証を作る。
