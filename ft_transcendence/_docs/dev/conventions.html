014分割の原則

分割の軸は「機能ごと」ではなく「リアルタイム×永続」×「FE×BE」の2軸。 ワードウルフはゲーム進行（Channel）とその前後（REST）で技術がきれいに分かれるため、 この軸なら4人の作業がファイルレベルでほぼ交差しない。レーンの定義は 実装フロー §06 が正で、ここでは運用ルールだけを決める。

レーン担当領域対応画面対向レビュー
A 進行中BEGameServer・Channel・フェーズ遷移—（配信の裏側）A ↔ B
（Channel契約を挟んで対面）
B リアルタイムFEChannelクライアント・ゲーム中画面08〜20
C 永続BEEcto・auth / users / rooms / friends のREST—（RESTの裏側）C ↔ D
（REST契約を挟んで対面)
D RESTFE + 基盤REST画面・make gen / CI / lint 管理01〜07 / 21〜24
  1. ペアは「契約を挟んだ対面」で組む。 AのPRはBが、BのPRはAがレビューする（C・Dも同様）。 自分が消費する側のコードをレビューするので、契約とのズレに一番早く気づける。
  2. レーン間のやり取りはコードでなく契約で行う。 「この形で返して」は口頭やSlackでなく 契約PR（§05の手順）で伝える。
  3. 画面の見た目は mock が正。 画面を作るときは _docs/mock/src/pages/ の 該当ページを移植し、データ境界だけを差し替える（データ前提の画面設計）。

02ディレクトリ所有マップ

「所有」= そのディレクトリ内は所有レーンが自由に変更してよく、他レーンは PR + 所有者レビュー必須。 矢印無しで2レーン以上が書く場所を作らないのが原則。 

frontend/src/
├── pages/            画面01-07, 21-24 → D ／ 画面08-20 → B
├── components/
│   ├── ui/           D（汎用部品。mockから移植）
│   ├── game-ui/      B（ゲーム固有部品）
│   └── layout/       D
├── hooks/            Channel系 → B ／ それ以外 → D
├── lib/              api-client → D ／ channel-client → B
└── types/            全員共有・生成物（手編集禁止。make gen のみ）

backend/lib/
├── word_wolf/
│   ├── contract/     全員共有・生成物（手編集禁止）
│   ├── accounts/ rooms/ friends/   C（Ectoコンテキスト）
│   └── games/        GameServer・進行ロジック → A ／ 結果の永続化 → C
└── word_wolf_web/
    ├── controllers/  C
    ├── channels/     A
    └── router.ex     共有ファイル（§06の運用に従う）
生成物ディレクトリの特例

frontend/src/types/ と backend/lib/word_wolf/contract/ は誰も「所有」しない。 変更は契約PR + make gen の結果のコミットだけで発生し、手で編集したらCI（make gen-check）で落ちる。

共通: 名前の正本は契約

エンドポイント・イベント・スキーマ・フィールドの名前は契約に書いてある通りに使う。 勝手に略さない（roomState を rs にしない）、勝手に訳さない（assignment を oday にしない）。コード内の語彙が契約とずれた瞬間、grepで追えなくなる。

04関数定義のルール

フロントエンド

// コンポーネントは named export の function 宣言（mockの流儀。default export・アロー代入は使わない）
export function GameTimer({ value, label = '残り時間', urgent }: GameTimerProps) { ... }

// propsの型は「コンポーネント名 + Props」で同ファイルに置く
interface GameTimerProps { ... }

// イベントハンドラは handle 始まり、渡すpropsは on 始まり
const handleSubmit = () => ...    // 内部
<WordCard onReveal={...} />       // props
  • 1関数50行以内・ネスト4段まで。超えたら分割のサイン（§05）。
  • early return で正常系を最後に書く（ガード節を上に集める）。
  • データは変更せず作り直す（push でなくスプレッド。Reactのstateは特に）。
  • API呼び出し・Channel操作をコンポーネント内に直接書かない。lib/ か hooks に置き、 コンポーネントは「型付きの関数を呼ぶだけ」にする。

バックエンド

# public関数には @spec。契約に対応する形は必ず生成型（Types.*）を使う
@spec payload() :: Types.health()
defp payload do ... end

# 分岐は if の入れ子でなく、関数節 + パターンマッチ + ガードで書く
def handle_in("chat.send", %{"text" => text}, socket) when is_binary(text) do ... end
def handle_in("room.ready", payload, socket) do ... end
  • public関数を上、defp を下に置き、モジュールを上から読めるようにする。
  • controller / channel は薄く保つ: 入出力の変換だけを書き、判断はコンテキスト （WordWolf.Rooms 等）か GameServer に置く。
  • 失敗は {:error, :room_full} のように契約の ErrorCode と対応するatomで返し、 HTTP/Channelへの変換は境界（FallbackController / Channelのreply）で一括して行う。

05ファイル分割のルール

  • 目安200〜400行、上限800行。上限を超える分割待ちの巨大ファイルを作らない。
  • 種類でなく機能で切る。utils.ts にゲームロジックを足さない — 投票の集計なら lib/vote.ts、フェーズ計算なら lib/phase.ts を作る。
  • FEの分割順序: ① JSXが長い → 子コンポーネントを同ディレクトリに切り出す ② state管理が長い → カスタムhookへ ③ 純粋な計算 → lib/ へ（ここだけ単体テスト必須）。
  • BEは1モジュール=1ファイル（Elixir標準）。コンテキストが太ったら rooms.ex を窓口に残して rooms/invite.ex のようにサブモジュールへ委譲する。
  • 切り出しは自レーンのディレクトリ内で行う。共有場所（components/ui/ 等）への昇格は 2レーン目の利用者が現れた時点で、利用者側がPRを出す。

06競合を避ける運用

4人並走で衝突するのは決まって「共有ファイル」。以下の4つだけ特別扱いする。

共有ファイル運用
router.ex / ルーティング定義行を足すだけのPRにして即マージ。他の変更と混ぜない
index.css（デザイントークン）トークン追加はD経由。各画面のスタイルは各ファイルで
mix.exs / package.json依存追加は単独PR。バージョンは 使用ツール の固定方針に従う
契約（_docs/spec/api/*.yaml）契約PR（§05）。FE/BE両担当のApprove必須

ブランチ戦略（main / develop）

main                  安定版。develop からのマージだけを受け付ける（直コミットしない）
└── develop           統合ブランチ。全レーンのPRの向き先
    ├── a/<内容>      レーンブランチ。develop から切り、develop へPR
    ├── b/<内容>      （例: b/lobby-page, d/auth-pages）
    ├── c/<内容>
    └── d/<内容>
  • main は常にデモできる状態を保つ。 develop → main のマージは「動く区切り」 （週の締め・マイルストーン）でのみ行う。
  • 契約PR（yaml + 生成物）も develop へ。 4レーンが同じ develop を見るので、型のズレが統合前に出る。
  • hotfix だけ main から切ってよい。マージ後に develop へも取り込む。
  • ブランチ名: <レーン>/<内容>（例: d/auth-pages, a/game-server-voting）。 誰のレーンの作業か履歴から分かるようにする。
  • コミット: feat: / fix: / refactor: / docs: / test: / chore: の接頭辞（既存履歴と同じ）。
  • マージ順で迷ったら: 契約PR → 生成物 → BE → FE。逆流（FEの都合で契約を直す）は 契約PRからやり直す。

07AIツールの使い分け（AGENTS.md / skills）

各自が Claude Code / GitHub Copilot / Codex など別々のAIツールを使っても 同じ規約で作業できるよう、エージェント向けルールはルートの AGENTS.md を正本にする。

ツール読むファイル扱い
共通（Codex / Cursor / Copilot coding agent 等）AGENTS.md（ルート）正本。ルール変更はまずここ
Claude CodeCLAUDE.md（@AGENTS.md を取り込み）+ .claude/skills/skills は手順の自動実行用（下記）
GitHub Copilot（VS Code チャット）.github/copilot-instructions.mdAGENTS.md の要約。AGENTS.md 変更時に反映する
BE作業時backend/AGENTS.md（phx.new 生成）Phoenix固有の指針。近い方が優先される

Claude Code では繰り返す作業手順を .claude/skills/ にスキルとして定義し、 同じ手順・同じ規約で自動実行できるようにする。リポジトリ直下に置くので4人全員に共有される。 

.claude/skills/
├── README.md            スキルの書き方（テンプレート付き）
└── add-endpoint/
    └── SKILL.md         エンドポイント追加の手順（実装フロー §11 の実行版）
  • 1スキル = 1タスク。 ディレクトリ名は kebab-case、本体は SKILL.md 固定。
  • frontmatter の description に「何をするか」と「いつ使うか」を書く。 エージェントはこれを見て発動を判断するため、トリガー条件が一番重要。
  • 手順の正本は docs 側に置き、スキルからリンクする。 両方に書くと必ず片方が古くなる。 スキルには「実行するコマンドと順序」だけを書く。
  • 追加・変更は develop へのPR。 所有レーンなし（全員共有）、レビューは誰でもよい。 他ツール（Copilot等）しか使わないメンバーは、同じ手順が AGENTS.md と この規約に文書として存在するため、そちらを参照して手で実行する。

08統合の動線（mock → 実結合）

4レーンが並走して最後の1回で結合しないための動線。原則は 「結合＝向き先の切り替えだけ」— コードに mock 分岐を書かず、 接続先を1つの環境変数で段階的に差し替える（データ前提の画面設計の3段階）。 

段階0  契約を固める     対象スライスの契約PR + make gen（全員のスタート地点）
段階1  fixture         通信なしで画面・関数を作る。誰にも依存しない
段階2  偽物に接続       D: make mock（prism :4010）に向ける ── 契約にだけ依存
                        B: fixture payload を流す偽socketで画面を駆動（channel-client 内で完結）
段階3  実物に切替       VITE_API_BASE を実BE（:4000 / Caddy）へ ── コード変更ゼロで結合
検証    make proxy（契約逸脱の検出）+ fixtures 共有テスト + compose スモーク
週次    develop 上で全結合 → 動く区切りで main へPR
  • 切替は VITE_API_BASE の1変数だけ（frontend/src/lib/api-client.ts）。 未指定なら同一オリジン（= Caddy 経由）に向く。
  • fixtures（期待JSON）が A↔B / C↔D の合意点。 契約PRで手書きし、 FE（vitest）とBE（ExUnit）が同じファイルを読む。結合前にすり合わせが終わる。
  • Channel は prism でモックできないため、Bは fixtures を流す偽socketで作り、 Aの実装後に channel-client.ts の中身だけを phoenix クライアントへ差し替える。 画面側のコードは触らないのが正しい状態。
  • 週1回の「全結合日」を決める。 compose up で PoC スモーク （ログイン → 部屋作成 → 参加 → 開始）を全員で通し、通ったら develop → main のPR。
