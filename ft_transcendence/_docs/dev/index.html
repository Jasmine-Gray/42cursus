013つの原則

  1. 契約が唯一の正 — _docs/spec/api/openapi.yaml と asyncapi.yaml。 実装を先に書いて契約を後追いさせない。
  2. 型は生成物 — レスポンス型・リクエスト型・入力検証スキーマ・Channelのpayload型を手で書かない。
  3. 実装は生成物を経由する — 生の fetch と手書きの interface を使わない。 バックエンドも契約から読み込んだスキーマで入出力を検証する。

この3つが守られていれば、フロントとバックが同じ形を別々に推測する事故が構造的に起きない。 「フロント/バックで役割が被らない」ための土台もここにある。

02全体像

契約 → 生成物 → 実装 → CI の一方向。逆流（実装から契約を直す）は必ず (1) の契約PRを経由する。

03手で書くもの / 書かないもの

対象扱い置き場所 / 根拠
レスポンス・リクエストのTS型生成frontend/src/types/api.d.ts
APIクライアント生成openapi-fetch が契約の型を読む。ラッパは認証とベースURLのみ
フォーム入力の検証契約を直読み契約の components.schemas を ajv + @hookform/resolvers/ajv へ渡す。minLength 等を手で写さない
Channel payloadの型生成frontend/src/types/ws/events.ts と contract/events.ex
イベント名 → payload型の対応生成ws/events.ts の RoomEventPayloads / UserEventPayloads と Contract.Events
fixtures（期待JSON）手書きcontracts/fixtures/。契約PRで更新し、FE/BE両方のテストが読む
エラー文言（UI日本語）手書き / FEBEは ErrorCode の18値を返すだけ
Ectoスキーマ・Changeset手書き / BEDBの制約が主。API形は契約側で検証する
ゲームルール（GameServer）手書き / BE契約に出ない内部状態。backend-spec.md が正
生成物の中身の修正禁止直したいときは契約を直して再生成する
手書きの interface User 等禁止生成物からimportする
生の fetch("/api/...")禁止パス文字列の打ち間違いが型で落ちなくなる

04初期セットアップ（W1で1回）

フロントエンド

cd frontend
npm i openapi-fetch react-hook-form @hookform/resolvers ajv ajv-formats phoenix
npm i -D openapi-typescript @types/phoenix
npm i -D oxlint prettier prettier-plugin-tailwindcss typescript vitest @vitest/coverage-v8

バックエンド（mix.exs）

{:open_api_spex, "~> 3.22"},
{:yaml_elixir, "~> 2.12"}

契約YAMLを読み込んで %OpenApiSpex.OpenApi{} にする。コードから仕様を生成する向きには使わない（正本がElixirコードへ移ってしまう）。

# lib/word_wolf_web/api_spec.ex
defmodule WordWolfWeb.ApiSpec do
  @behaviour OpenApiSpex.OpenApi

  @spec_path "../_docs/spec/api/openapi.yaml"

  @impl true
  def spec do
    @spec_path
    |> Path.expand(__DIR__)
    |> YamlElixir.read_from_file!()
    |> OpenApiSpex.OpenApi.Decode.decode()
  end
end

生成コマンドをMakefileに集約

# 実物はリポジトリ直下の Makefile（make help で一覧）
gen: gen-frontend gen-backend

gen-frontend:
	npx --yes openapi-typescript@7.13.0 _docs/spec/api/openapi.yaml \
	  -o frontend/src/types/api.d.ts
	python3 _tools/gen-contract-types.py --only frontend

gen-backend:
	python3 _tools/gen-contract-types.py --only backend

spec-lint:
	npx --yes @redocly/cli@2.46.1 lint _docs/spec/api/openapi.yaml
	npx --yes @asyncapi/cli@6.0.2 validate _docs/spec/api/asyncapi.yaml

CIで「手編集」を機械的に禁止する

- run: make spec-lint
- run: make gen-check    # 生成物の手編集と未コミットで落ちる

lint・整形・静的解析・テストのツールとCIの実行順は 使用ツール §03 にまとめた。すべて2026-08-19時点の最新に揃え、 4週間の期間中はバージョンを上げない。

なぜ生成物をコミットするか

生成コマンドが通らない環境でもビルドでき、レビューで型の変化が差分として見える。 代わりに上のCIチェックで「手編集された生成物」を落とす。

05日々の開発サイクル

  1. 契約PR（実装を1行も含めない）

    起案者 → FE/BE両担当のApprove必須

    openapi.yaml / asyncapi.yaml と contracts/fixtures/ だけを変更する。 make spec-lint と build-docs.sh を通してHTMLも一緒にコミットする。

  2. make gen

    全員（各自の作業開始時）

    生成物を更新する。型エラーが出た箇所が、契約変更の影響範囲そのものになる。

  3. BE: スタブ → 実装

    BE担当（進行中=A / 永続=C）

    まず契約どおりの固定値を返すスタブを置き、CastAndValidate を通す。 FEはこの時点で実サーバーを叩ける。以降スタブの中身を実装に差し替えるだけで、FEのコードは変更不要が正しい状態。

  4. FE: 生成物で実装

    FE担当（リアルタイム=B / REST=D）

    openapi-fetch でエンドポイントを呼び、フォームは契約のschemaを @hookform/resolvers/ajv 経由でRHFに挿す。 BEが未実装なら prism mock を向ける。

  5. 検証

    CI

    BEはExUnitで assert_operation_response(conn, "operationId")。 FEはvitestでfixtureを検証。CIで prism proxy を実BEに当てて契約逸脱を落とす。

  6. マージ

    対向ペアがレビュー（A↔B / C↔D）

    BE実装PRとFE実装PRは分ける。履歴に分担が残り、Subjectの「作業分担が見えること」も満たす。

07WebSocket（Channel）の扱い

AsyncAPI 3.1.0 を扱えるコードジェネレータは存在しない（@asyncapi/modelina は 3.0.0 まで対応で、 3.0.0 に落としてもpayloadが AnonymousSchema_16 のような名前になる）。 契約をツールに合わせて曲げる代わりに、_tools/gen-contract-types.py で両言語分を生成する。

生成されるもの出力
payload型（15イベント + 6スキーマ） frontend/src/types/ws/events.ts / contract/events.ex
イベント名の定数（方向・チャンネル別） CLIENT_EVENTS / SERVER_ROOM_EVENTS / SERVER_USER_EVENTS、 Events.client_events/0 ほか
イベント名 → payload型の対応表 ClientEventPayloads / RoomEventPayloads / UserEventPayloads

手書きで残るのはfixturesだけ。contracts/fixtures/ws/phase.changed.json のように 1イベント1ファイルにし、FEはvitest + ajv、BEはExUnitで同じファイルを読む。 

// 生成された対応表を使う。イベント名もpayload型も手書きしない
import type { RoomEventPayloads } from "@/types/ws/events";

function onRoom<E extends keyof RoomEventPayloads>(
  channel: Channel,
  event: E,
  handler: (payload: RoomEventPayloads[E]) => void,
) {
  channel.on(event, handler);
}
# Elixir側も生成された型と定数を使う
alias WordWolf.Contract.Events

@spec broadcast_phase(String.t(), Events.phase_changed()) :: :ok
def broadcast_phase(room_id, payload) do
  Endpoint.broadcast!("room:" <> room_id, "phase.changed", payload)
end
秘密情報の原則

user:{userId} のpayload型を room:{roomId} のハンドラで参照していないか、 レビューで必ず確認する。RoomEventPayloads と UserEventPayloads が別のマップとして 生成されるので、型が通らないこと自体がチェック機構になる。

08契約を変えたくなったとき

  1. 実装を止めて、変更内容をSlack等で共有する（黙って実装を進めない）
  2. 契約PRを立てる — YAML + fixtures + 生成HTML（build-docs.sh）のみ
  3. FE/BE両担当がApprove。ここで「どちらが持つか」も同時に決める
  4. マージ後、各自 make gen。型エラーの出た箇所が対応すべき範囲
  5. 同じスプリント内でFE・BE双方のテストを更新する

「実装が先に進んでしまったので契約を後から合わせる」は禁止。契約が実装の追認になると、生成物を信頼できなくなる。

09ツール

選定の原則

生成するのは型まで。実行時コードは生成しない。 42の評価では自分が説明できないコードは失格になり得るため、生成物は型と検証スキーマに留め、 クライアント処理・hooks・状態管理は手で書く。この一線を引くと、必要なツールは下表で足りる。

10着手前に決めること

未決 — 型生成の導入より先に決める

1. 認証方式。 openapi.yaml は bearerAuth（セッショントークン）だが、 architecture/tech-stack.md §4 は「HttpOnly Cookie / トークンをLocalStorageに置かない」。 Bearerならクライアントラッパがトークンを保持し、Cookieなら何も持たない。生成後に直すと作り直しになる。

2. ゲーム中操作の経路。 tech-stack.md §3 は「原則Channel」だが、契約と backend-spec.md では start / vote は HTTP POST（配信のみChannel）。契約が正なので §3 を修正する。

11実例: /health で一周する

GET /health は実用とexampleの2役を持つ。 実用としてはdocker-composeの healthcheck・監視・疎通確認に使う本物のエンドポイント。 exampleとしては「契約 → 型生成 → 実装 → 検証」を最小構成で一周したリファレンス実装で、 新しいエンドポイントを足すときはこの節の差分をそのまま真似る。

1. 契約に書く（openapi.yaml だけを編集）

# paths: に追加。認証不要なので security: [] を明示
/health:
  get:
    tags: [system]
    operationId: getHealth
    security: []
    summary: 死活監視
    responses:
      '200':
        content:
          application/json:
            schema:
              allOf: [{$ref: OkEnvelope}, {data: {$ref: Health}}]  # 実物は省略なし

# components/schemas: に追加
Health:
  type: object
  required: [service, version, time]
  properties:
    service: {type: string, const: wordwolf-api}
    version: {type: string}
    time: {type: string, format: date-time}

2. lint → 生成 → モック確認

make spec-lint   # 契約の検証（Redocly + AsyncAPI CLI）
make gen         # frontend/src/types/ と backend/.../contract/ が更新される
make spec-docs   # HTML版仕様書も追随させる
make mock        # :4010 で契約どおりの偽サーバーが立つ

curl -s localhost:4010/health
# {"status":"ok","data":{"service":"wordwolf-api","version":"0.1.0","time":"2026-08-20T00:00:00Z"}}

生成された型（抜粋）。どちらも手で書いていない。

// frontend/src/types/api.d.ts（openapi-typescript が生成）
"/health": { get: operations["getHealth"]; ... };

# backend/lib/word_wolf/contract/types.ex（_tools/gen-contract-types.py が生成）
@type health :: %{
        required(:service) => String.t(),
        required(:version) => String.t(),
        required(:time) => String.t()
      }

3. FE: 生成型で呼ぶ

import createClient from "openapi-fetch";
import type { paths } from "@/types/api";

const client = createClient<paths>({ baseUrl: "/api" });  // BE未実装なら :4010 に向ける

const { data, error } = await client.GET("/health");
// data の型は契約から推論される。パスのtypoはコンパイルエラー

4. BE: 生成型を @spec に使う

defmodule WordWolfWeb.HealthController do
  use WordWolfWeb, :controller
  alias WordWolf.Contract.Types

  @spec health_payload() :: Types.health()   # 契約とのズレをDialyzerが検出
  defp health_payload do
    %{service: "wordwolf-api", version: "0.1.0",
      time: DateTime.utc_now() |> DateTime.to_iso8601()}
  end

  def show(conn, _params), do: json(conn, %{status: "ok", data: health_payload()})
end

5. 検証

make gen-check   # CIで生成物の再生成忘れ・手編集を落とす
make proxy       # :4011 経由で実BEを叩き、契約逸脱をエラーにする
この節の使い方

エンドポイント追加のPRは、必ずこの1〜5と同じ順で進める。 1が契約PR、2〜4が実装PR（§05 の分割どおり）。 /health の契約差分は git log -- _docs/spec/api/openapi.yaml で参照できる。
